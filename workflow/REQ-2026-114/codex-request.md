# REQ-2026-114 리뷰 요청

## 배경

승인 증거는 티켓의 feature 브랜치에 커밋된다. **그 브랜치가 병합되지 않으면 증거는 메인라인에
도달하지 않는다.** 이 사실이 어디에도 적혀 있지 않고, 발생해도 알 방법이 없다.

**실측**(소비자 3곳·271티켓·리뷰호출 2,089건·16일):

| | 호출 | 디스크 아카이브 | 유실 |
|---|---:|---:|---:|
| 합계 | 2,089 | 2,024 | **65 (3.1%)** |

🔴 **사라지는 쪽이 실패 기록이다** — 유실분 needs-fix **66.2%** vs 잔존 47.9%.
따라서 아카이브 기반 회고 분석은 **실패를 체계적으로 과소계상**한다.

메커니즘 확인: 도구에 `responses/`를 지우는 코드가 없다. git 추적 결과 유실 티켓의 증거는
**미병합 브랜치에만** 존재한다. MBTI가 0%인 것은 17티켓 전부 병합된 신생 프로젝트라서다 —
**유실은 무작위가 아니라 시간이 지나며 쌓인다.**

## 🔴 D25 확장이 **원리적으로 불가능**하다는 확인 (착수 전 조사)

처음에는 D25(종결됐지만 trunk 미도달)를 확장하려 했다. D25의 판정 입력은 **워킹트리의
close proof**다. 그런데 유실 상위 티켓 `REQ-2026-025`·`009`·`062`는

> **close proof가 워킹트리·main·전 브랜치 어디에도 없다** — 종결된 적 없는 **버려진 티켓**이다.

찾을 close proof가 없으므로 그 계열 검사로는 잡을 수 없다. **다른 신호가 필요하다.**

## 변경 요약 (6파일)

**신호를 리뷰 호출 로그로 바꿨다.** `workflow/.review-calls.jsonl`은 gitignored·워킹디렉터리
상주라 브랜치와 함께 사라지지 않고, "리뷰를 받았다"는 사실이 남는다. 유실 65건을 측정한 방법이
정확히 이것이다.

| 파일 | 변경 |
|---|---|
| `scripts/req/req-doctor.ts` | 새 검사 **D30**(WARN 전용) + 순수 판정 + `main()` 배선 |
| `docs/guarantees.md` · `.en.md` | `보장하지 않는 것`에 브랜치-지역성 명시 |
| `docs/ssot-design/07…md` | §3 정본 표에 D30 |
| `tests/unit/doctor-stranded-evidence.test.ts` (신규) | AC-1~AC-4 |
| `CHANGELOG.md` | Unreleased |

**노이즈를 실제 데이터로 측정하고 설계에 반영했다:**

| 프로젝트 | 리뷰받은 티켓 | trunk에 증거 없음 |
|---|---:|---:|
| yammy | 141 | 7 (알려진 유실 2 + 최근 5 — 진행 중 추정) |
| lean | 126 | 5 (알려진 유실 1 + 최근 4) |
| MBTI | — | `origin/main` 없음 → **판정 불가** |

진행 중 티켓이 섞인다. **기간 임계(age threshold)로 거르지 않고 리뷰 횟수를 함께 보인다** —
`REQ-2026-025(리뷰 8회)`와 `REQ-2026-140(리뷰 1회)`는 읽는 즉시 구별된다.
근거 없는 임의 임계를 넣지 않는다는 이 저장소의 원칙에 따른 선택이다.

## phase-1 r02에서 고친 것 — r01 의견 반영

**지적**: 로그가 **통째로 손상**되면 빈 Map이 되어 D30이 *"리뷰 증거가 모두 trunk에 반영됨"* 이라고
표시한다 — 판정 불가와 구별되지 않는다. **맞는 지적이다.** 아무것도 모르는데 괜찮다고 단언하는 것이고,
이 저장소가 반복해서 고쳐 온 결함 유형이다.

→ 비어 있지 않은 줄이 하나라도 있는데 **전부 파싱에 실패하면 `null`(판정 불가)** 을 낸다.
부분 손상은 종전대로 건너뛴다(나머지 관측은 유효하다).
**빈 파일은 빈 Map이 맞다** — "아직 리뷰가 없다"는 정상 상태이지 판정 불가가 아니다.
그 구별을 테스트 2건으로 고정했다.

## 🔴 도그푸딩 — 이 저장소에서 즉시 발화했다

구현 직후 이 저장소에서 `req:doctor`를 돌리자 D30이 바로 잡았다:

```
[req:doctor] WARN D30: 리뷰 증거가 trunk(main)에 없는 티켓 2건 —
  REQ-2026-026(리뷰 6회) · REQ-2026-041(리뷰 6회). 진행 중이면 정상입니다. …
```

둘 다 **실제로 종료·폐기된 티켓**이고, 각각 유료 리뷰 6회를 소비했는데 그 증거가 메인라인에 없다.
설계가 겨냥한 현상이 **합성 픽스처가 아니라 이 저장소의 실제 이력에서** 재현됐다.

동시에 **노이즈가 낮다는 것도 확인됐다** — 이 저장소의 100여 티켓 중 2건만 걸렸다.

## 리뷰 포인트

1. **신호 선택이 맞는가** — close proof로는 못 잡는다는 판단(위 실측)과, 리뷰 호출 로그를
   대체 신호로 쓰는 것. 로그가 gitignored라 **사용자가 지우면 진단도 사라진다**는 한계는 감수했다.

2. **노이즈 처리** — 진행 중 티켓을 포함한 채 리뷰 횟수로 구별하게 했다. WARN 전용이고
   "유실됐다"고 단정하지 않는다. 이 절충이 맞는지, 아니면 오히려 무시당할 안내인지.

3. **판정 불가를 조용히 통과시키는 것**(trunk ref 없음·로그 없음). D25가 같은 규칙을 쓰는
   근거를 그대로 따랐다 — 오탐이 잦으면 사람이 doctor 출력 전체를 무시한다.
   실측으로 `origin/main`이 없는 소비자가 실재한다.

4. **`ls-tree` 재사용**. D25가 이미 읽는 `trunkPaths`를 그대로 쓴다(git 호출 증가 0).
   D25 주석이 "티켓마다 `git log`를 돌리면 80회"라고 경계한 지점과 같은 맥락인지.

5. **보장 문서에 실측 수치를 넣은 것.** 추상적 경고("증거가 안 남을 수 있습니다")보다
   구체적 수치가 낫다고 판단했는데, 그 수치가 특정 시점의 스냅샷이라 낡을 수 있다.

6. **AC-4(실 진입점 e2e)를 반드시 둔 이유** — D30은 `main()`이 로그 파일을 읽어 입력을 만든다.
   순수 함수만 테스트하면 배선 끊김을 못 본다(REQ-2026-083·097·099 실증).
