# REQ-2026-066 요구사항

delivery set + stopGate merge

## 배경

사용자가 요구한 세 번째 멈춤 지점:

> REQ도 모두 수행하고 모든 요구사항 처리 후 **main 브랜치 머지 전에** 멈춘다.

이것이 필요한 이유는 실제 작업 형태다 — 상위 요구사항이 커서 REQ를 분리하거나, 검수가 8라운드까지
가도 승인이 안 나 REQ를 더 잘게 나누거나, 여러 설계·개발 계획 문서를 순차 진행하면 **REQ가 여러 개
발행되고 각각 하나의 feature 브랜치에서 진행된다.** 그 묶음이 다 끝날 때까지 main 병합을 미루고
마지막에 한 번만 멈추고 싶다는 것이다.

**이것은 전역 백로그가 아니다.** 도구가 "모든 요구사항이 끝났는지"를 스스로 판정하지 않는다 —
사용자가 묶음을 **명시적으로 만들고 명시적으로 닫는다.** 닫히기 전까지 REQ 추가는 자유다.

REQ-2026-063이 `stopGate`를 도입했지만 값은 `phase`/`req` 둘뿐이다. `merge`는
**동작(묶음 모델)이 함께 있어야 성립**하므로 그 REQ에서 의도적으로 빠졌다.

## 요구사항

| # | 내용 |
|---|---|
| **R1** | 사용자가 **상위 작업 묶음(delivery set)** 을 만들고 닫는다 |
| **R2** | 묶음에 속한 REQ들이 **순차** 진행되고, 완료분이 묶음 브랜치에 반영된다 |
| **R3** | 검수 실패로 REQ를 **더 잘게 나누는 경로**가 있다(successor 교체) |
| **R4** | 묶음이 닫히고 모든 member가 종결되면 **통합 직전에 멈춘다** |
| **R5** | `stopGate: "merge"` 선택지가 열린다 |

## 🔴 제약

### C1. 순차 불변식 — 활성 REQ는 하나
`begin`은 **현재 delivery HEAD에서** feature를 만들고, 그 REQ가 종결되기 전에는 다음 `begin`을 거부한다.
이 불변식 아래서는 반영 시점에 delivery HEAD가 feature의 조상이므로 **충돌이 구조적으로 발생하지 않는다.**

### C2. 🔴 충돌은 **정상 경로가 아니라 fail-closed 입력**이다
자동 rebase·자동 충돌 해결을 하지 않는다 — 충돌 해결은 **새 코드 변경**이고, 재검수 없이 트리에 들어가면
게이트가 뚫린다. 기대 상태와 어긋난 입력은 **거부**한다(merge·레코드 write 0건).

### C3. 🔴 레코드의 읽기 정본은 **delivery 브랜치**다
feature 브랜치에도 레코드 파일이 물리적으로 남지만(git 분기 특성), 그 사본은 분기 시점에 고정되어
**stale**이다. 그것으로 "모든 member 종결"을 판정하면 **조기 정지**가 발생한다.
사본을 지우려 하면 반영 시 delete/modify 충돌이 나 C1의 무충돌 불변식을 스스로 깬다.

### C4. 🔴 `superseded` 증거는 delivery에 **보존**한다
교체된 parent의 feature ref는 미승인 변경을 담은 채 병합되지 않으므로 **삭제될 수 있고**,
그러면 SHA가 가리키던 object가 GC되어 검증 원본이 사라진다. 해시 포인터로는 부족하다.

### C5. 🔴 종결 판정은 **재귀적**이어야 한다
"유효 successor가 있다"만으로는 순환(`R1→R2→R1`)이나 `superseded`만 이어지는 체인이 전부 종결로 보인다.

### C6. 병합 실행은 범위 밖
CommitGate는 지금까지 main을 건드린 적이 없다. `delivery → main` 병합까지 수행하면 protected branch·
push·PR이 blast radius에 들어온다. **"닫히면 반드시 멈추고 그 승인을 기록하는 것"까지**가 책임이다.

### C7. v1 동시성 보장 범위
**단일 활성 워크트리 + 협조적 작업자**만 보장한다(이 저장소의 기존 보장 경계). 로컬에서 관측 가능한
불일치는 fail-closed로 막고, **원격 동시 작업은 비목표**다(fetch 없이 알 수 없다).

## 🔴 비목표

| 비목표 | 이유 |
|---|---|
| **`delivery → main` 병합 실행** | C6 |
| **원격 lock / PR 대기열** | C7 |
| **전역 백로그·자동 완료 판정** | 사용자가 묶음을 만들고 닫는다 |
| **여러 묶음 동시 진행** | v1은 활성 묶음 1개. 늘리면 root 해소·활성 판정이 복잡해진다 |

## 🔴 릴리스 제약

**p1~p3를 한 릴리스로만 공개한다.** `create`/`begin`만 배포되면 사용자가 **integrate·seal·approve가 없는
묶음**을 만들 수 있고, 그 묶음은 안전하게 통합할 방법이 없다(정상 경로 단절).

## 수용 기준

1. `delivery create` → 묶음 브랜치와 레코드가 생긴다.
2. `delivery begin` → delivery HEAD에서 feature가 생기고 REQ가 member로 등록된다.
3. 활성 member가 있으면 다음 `begin`이 **거부**된다.
4. `delivery integrate` → feature가 delivery에 반영되고 레코드가 **같은 커밋**에서 갱신된다.
5. 기대 상태와 어긋나면(base 불일치·조상 아님) **write 0건으로 거부**된다.
6. `delivery begin --successor-of` → parent가 `superseded`가 되고 **미승인 변경은 병합되지 않는다**.
7. `superseded` 증거가 delivery 레코드에 **사본으로** 보존된다.
8. 종결 판정이 **재귀적**이다 — 순환·`superseded`만의 체인은 종결이 아니다.
9. `seal` 후 모든 member가 종결되면 `AWAIT_HUMAN`이 뜨고, `approve`가 승인을 기록한다.
10. `stopGate: "merge"`가 선택 가능해진다.
11. `npm test` green · `tsc --noEmit` 0.
