# REQ-2026-095 요구사항

여러 줄 커밋 메시지 붕괴 — 정본 경로가 안전한 길을 가리키게

## 배경

소비자 버그 리포트(2026-08-01, `0.15.0` · Windows 11 / pnpm). `req:commit`에 여러 줄 커밋 메시지를
`-m`으로 넘기면 **본문이 통째로 사라지고** 줄바꿈이 리터럴 두 글자 `\n`으로 바뀐 채 subject 한 줄에
들어간다. 소비 저장소의 커밋 6건이 그 상태로 main에 병합됐다.

리포트는 원인을 `pnpm run`의 인자 재직렬화로 지목했다. **확인한 결과 맞지만 범위가 더 넓고,
리포트의 제안 하나는 실측으로 반증된다**(§2·§3).

## 1. 실측 — pnpm 문제가 아니라 Windows `.cmd` shim 문제다

Windows 11 Pro 26200 / Node 24.18.0 / npm 11.16.0 / pnpm 9.9.0에서 argv를 그대로 출력하는
스크립트로 전 경로를 직접 재현했다(`process.argv.slice(2)`를 JSON으로).

| 호출 경로 | 여러 줄 `-m` 결과 |
|---|---|
| `node <script>` | ✅ 개행 보존 |
| `pnpm exec node <script>` | ✅ 개행 보존 |
| **`npm run <script> -- -m`** | 🔴 **개행 이후 통째로 소실** |
| `pnpm <script> -m` | 🔴 리터럴 `\n` 두 글자(리포트와 일치) |
| **`npx <bin>`** | 🔴 소실 |
| **`pnpm exec <bin>`** | 🔴 소실 |
| **`npx tsx <script>`** | 🔴 소실 |
| **`--message-file`**(전 경로) | ✅ **온전** |

### 1.1 🔴 npm이 pnpm보다 나쁘다 — 조용히 잃는다

pnpm은 이스케이프하므로 **내용이 남고 탐지 가능**하다(리터럴 `\n`이 보인다).
npm·npx는 개행 뒤를 **버린다**. 사용자는 본문이 사라진 것을 알 방법이 없고, 도구도 탐지할 수 없다 —
받은 문자열이 그냥 짧을 뿐이다. **이 저장소를 포함해 `packageManager: "npm"`인 소비자가 더 위험하다.**

명령 주입은 아니다 — 개행 뒤 텍스트가 셸에서 실행되는지 부작용(파일 생성)으로 확인했고, 실행되지 않았다.

### 1.2 안전한 것은 shim을 거치지 않는 직접 호출뿐이다

`node`·`pnpm exec node`만 온전하다. 둘 다 **문서화된 경로가 아니다.**
즉 사용자가 따를 수 있는 모든 정본 경로가 여러 줄 `-m`을 망친다.

## 2. 🔴 리포트 제안 #4는 반증됐다

리포트는 "`pnpm exec commitgate req:commit …`를 제시하라(`pnpm exec`는 정상 동작 확인)"고 했다.
그들이 확인한 것은 **`pnpm exec node echo-argv.mjs`** — `node`를 직접 부르는 형태다.
실제 제안 형태인 **`pnpm exec <bin>`은 `.cmd` shim을 거쳐 똑같이 잘린다**(위 표, 실측).
**이 제안은 채택하지 않는다.**

## 3. 🔴 리포트 제안 #1은 이미 구현돼 있다

`--message-file <path>`가 **REQ-2026-018로 이미 들어가 있다**(`req-commit.ts`):
`-m`과 상호배타 · `REQ_COMMIT_MESSAGE_FILE` 환경변수 fallback · 절대경로 정규화 · 존재검증 · git `-F` 사용.
그 코드 주석이 문자 그대로 *"messageFile 경로는 pnpm/Windows argv newline 이스케이프를 회피"* 라고 적혀 있고,
`docs/workflow.md`에도 예시가 있다.

**그런데 정본 경로가 그것을 가리키지 않는다.** `req:next`가 RUN/AWAIT_HUMAN으로 내는 커밋 명령은
항상 `-m "<자리표시자>"`이고(`req-next.ts`의 `commitCmd`·`autoCommitCmd`), `AGENTS.md`는
*"RUN이면 출력된 명령을 **그대로** 실행하라"* 고 계약한다.
→ **정본을 따르면 반드시 함정을 밟는다.** 리포트의 지적이 정확하다.

즉 이 REQ가 고칠 것은 **기능이 아니라 안내**다.

## 4. 요구사항

- **R1 (정본 안내)** `req:next`가 커밋 명령을 낼 때, `-m`이 **한 줄용**임을 명시하고 **여러 줄은
  `--message-file`** 로 간다는 것을 같은 출력에서 알린다. 🔴 RUN 명령 자체는 **그대로 실행 가능한 상태**로
  유지한다(자리표시자만 채우면 되는 현재 계약을 깨지 않는다 — REQ-2026-058 F-3이 그것을 보장했다).
- **R2 (git 규약)** `-F`를 `--message-file`의 별칭으로 받는다(`git commit -F`와 같은 규약).
- **R3 (탐지 가능한 것만 경고)** `-m` 값에 리터럴 `\n`이 있고 **실제 개행이 하나도 없으면** 경고한다.
  🔴 **자동 복원하지 않는다** — 본문에 정말 `\n`이라고 쓴 경우와 구분할 수 없다(리포트의 요청과 동일).
  🔴 경고일 뿐 **차단하지 않는다**. npm의 조용한 절단은 원리적으로 탐지 불가이므로 이 경고는
  pnpm 계열만 잡는다 — 그 한계를 문구에 드러낸다.
- **R4 (문서)** 실측표와 "여러 줄은 반드시 `--message-file`"을 사용자 문서에 남긴다.
- **R5 (무회귀)** 한 줄 메시지의 **동작**은 바뀌지 않는다. `req:next`가 내는 커밋 명령의 **구조**도
  그대로다 — 여전히 `-m <자리표시자>`이고 자리표시자만 채우면 **그대로 실행 가능**하다
  (REQ-2026-058 F-3 계약).
  🔴 **자리표시자의 표기는 바뀔 수 있다** — `(한 줄)` 제약을 자리표시자 자신이 말하게 하는 것이
  이 REQ의 수단 중 하나다(01-design DEC-1). 무회귀 대상은 **구조와 실행 가능성**이지 문구가 아니다.

## 5. 범위 밖

- **`--message-stdin`**(리포트 #2). `--message-file`로 충분하고, 같은 목적의 두 번째 메커니즘은
  유지 부담만 늘린다. 필요해지면 별도 REQ.
- 이미 붕괴한 커밋의 rewrite. 소비자도 하지 않기로 했다 — `approvals.jsonl`의 source SHA 결속이 깨진다.
- 상류(npm/pnpm/npx) 수정. 우리 통제 밖이다.

## 6. 완료 기준

- `req:next`의 커밋 안내에 `--message-file` 경로가 **함께** 나온다(RUN 명령은 여전히 실행 가능).
- `req:commit -F <path>`가 `--message-file`과 동일하게 동작한다.
- 리터럴 `\n`만 있는 `-m`에 경고가 뜨고, **커밋은 그대로 진행된다**.
- 한 줄 메시지 경로 무회귀(전체 스위트 그린).
