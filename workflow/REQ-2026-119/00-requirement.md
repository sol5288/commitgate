# REQ-2026-119 요구사항

phase 실효 위험 감지 — 민감 경로 D31 경고(관측 우선)

## 배경 (무엇이 문제인가)

위험도는 **티켓 생성 시 입력값**(`req:new --risk`, 기본 LOW)만 신뢰된다 — 소비자 272티켓 중
HIGH는 4건(1.5%)뿐이고, 리뷰어의 위험 평가는 deprecated(REQ-2026-084 DEC-3)라 게이트에 닿지
않는다. 그 결과 **티켓 전체 위험도와 phase의 실효 위험이 분리돼 있지 않다**: LOW 문서 티켓으로
시작해도 어느 phase가 결제 웹훅·인증·마이그레이션·비밀정보를 건드릴 수 있고, 그 사실을 어떤
표면도 알리지 않는다.

**강제가 아니라 관측부터 넣는 이유** — 이 저장소의 실측 선례 둘: ① 0.13.0의 block 기본값은
오판이었고 0.13.1에서 warn으로 정정, 강제는 opt-in으로 남았다. ② REQ-2026-066: 게이트 조건은
넣기 전 실제 데이터로 양방향 측정한다(19/19 불일치로 조건 하나를 기각한 실례). 민감 경로 패턴의
오탐률 데이터가 없는 상태에서 사람 확인을 강제하면 오탐이 곧 마찰이 된다. 이 REQ는 감지·표시·
기록까지 하고, 확인 강제(및 `stopGate` 단일 지배 원칙과의 조정)는 발화율 데이터가 쌓인 뒤
별도 REQ의 결정으로 남긴다.

## 요구

- **R1 · 민감 경로 감지(순수)** — staged 파일 경로가 민감 패턴에 일치하는지 판정한다.
  패턴은 소문자 부분 문자열 매치이고, 기본 목록은 보수적으로 좁게 유지한다(오탐이 경고 피로를
  만든다 — D30 개선의 근거였던 그 실측). 기본 목록에 무엇이 있는지는 설계가 확정한다.
- **R2 · config 확장** — `req.config.json`에 `riskPaths?: string[]`(선택). 지정 시 기본 목록을
  **대체**한다(합집합이 아니다 — 프로젝트가 자기 오탐을 제거할 수 있어야 한다). 미지정 = 기본 목록.
- **R3 · D31 진단(WARN 전용)** — staged 변경이 패턴에 일치하면 doctor가 WARN으로 일치 패턴과
  대표 경로를 표시한다: 티켓 위험도와 별개로 "이 phase의 실효 위험을 확인하라"는 안내.
  FAIL 불가 — 어떤 경우에도 커밋을 막지 않는다.
- **R4 · 정본 정합** — `D_CHECK_IDS` 등록 + D-체크 정본 표(`docs/ssot-design/07` §3) 갱신
  (등록부↔문서 일치 가드가 강제한다).

## 제약

- `userConfirmGate`·`stopGate`·커밋 게이트 무변경. 이 REQ는 진단 하나를 추가할 뿐이다.
- 실행 로그(`.doctor-runs.jsonl`)에는 기존 규칙대로 id·level만 실린다 — **경로는 subjects로도
  남기지 않는다**(REQ-2026-111·117의 저위험 식별자 원칙: 경로는 허용 목록 밖).
- 리뷰어에게 위험 평가를 다시 요청하지 않는다(REQ-2026-084 DEC-3 유지).
- 네트워크·유료 호출 없음.

## 완료 기준

1. 기본 패턴에 일치하는 staged 경로가 있으면 D31 WARN이 일치 패턴·대표 경로와 함께 발화한다.
2. 일치가 없으면 D31 OK — 기존 티켓·스위트에 새 WARN이 생기지 않는다(이 저장소 도그푸딩 포함).
3. `riskPaths` 지정 시 기본 목록이 대체된다(빈 배열 = 감지 비활성, 그것도 유효한 선택).
4. D31은 WARN까지만 도달한다(FAIL 경로 부재를 테스트로 고정).
5. 등록부·정본 표 가드가 그린이다.
6. 실행 로그 행에 경로가 실리지 않는다.
