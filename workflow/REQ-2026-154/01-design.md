# REQ-2026-154 설계

## DEC-1 — 결속 대조를 **소비 state 를 쓰기 전**으로 옮긴다 (결함 1·4)

지금은 대조가 `planEvidenceRecovery` 의 checkpoint 분기 하나에만 있다. 그것이 **판정 지점**이고,
`consume` 경로는 그 판정을 지나지 않는다. 대조를 **쓰기 직전**에도 둔다.

```
finalizeEvidenceAndConsume
  … already(=HEAD 에 소비 행 있음) 분기 …
  consumed = consumeState(…)
  🔴 [신설] HEAD 행에 결속이 있으면 sha256(serializeState(consumed)) 와 대조 → 다르면 throw
  writeState(consumed)
```

- 🔴 **정상 경로(`!already`)에는 대조가 필요 없다.** 그 경로는 결속을 **지금 만들어** 매니페스트에
  넣으므로 정의상 일치한다. 거기서 또 대조하면 자기 자신을 비교하는 동어반복이다.
- 🔴 **결속이 없는 옛 행은 건너뛴다**(하위호환 — REQ-2026-152 와 같은 규칙).
- 🔴 **write 전에 막는다.** 쓰고 나서 알면 이미 워킹 state 가 오염됐고, 그 상태가 다음 복구의
  입력이 된다(결함 1 의 4단계가 정확히 그 모양이다).
- 🔴 **대소문자를 정규화한다**(결함 4). `SHA256_RE` 가 `/i` 인 것은 **기존 계약**이므로 바꾸지
  않는다. 대신 **비교 양쪽을 소문자로** 맞춘다. `BindingLookup` 이 `sha` 를 **소문자로 정규화해
  돌려주는 것**이 정본이다 — 호출부마다 `toLowerCase()` 를 기억해야 하면 언젠가 빠진다.

### DEC-1a — 탈출구는 **검증한 뒤에만** 낸다 (설계 r01 P1)

🔴 **초안의 `git checkout -- <ticket>/state.json` 은 아무것도 되돌리지 못한다.** 이 결함을 만드는
경로(`req:repolicy --run`)는 바뀐 state 를 **checkpoint 커밋**하므로 그것이 곧 HEAD 다 — HEAD 에서
되돌리면 같은 값이 다시 온다. 이 저장소가 반복해 밟은 "실행 불가능한 안내"를 또 낼 뻔했다.

**두 번째 안도 실측으로 기각했다.** "`state.json` 을 건드린 커밋을 훑어 결속과 맞는 blob 을 찾자"는
그럴듯하지만 **찾을 것이 없다**:

```
$ git log --format="%h %s" -- workflow/REQ-2026-152/state.json
7649bc2 chore(REQ-2026-152): state checkpoint — phase … 소비
b596cf2 chore(REQ-2026-152): state checkpoint — phase … 소비
157e90d chore(REQ-2026-152): design-finalize — design 승인 approvals.jsonl·state 기록
fba9c51 chore(req): REQ-2026-152 티켓 생성
```

- **phase 승인 시점 state 는 커밋되지 않는다** — 티켓 생성 · design-finalize · **소비** checkpoint 뿐이다.
- design 승인은 state 를 커밋하지만, **그 경로는 이 결속을 만들지 않는다**(`absent` 라 대조를 건너뛴다).
- 🔴 **양쪽 모두 후보가 없다.** 넣었다면 죽은 코드였고, 이 저장소는 그것을 REQ-2026-152 에서
  한 번 겪었다("도달 불가일 수 있다"고 적은 코드가 사실은 살아 있었고, 반대로 여기서는 죽는다).

**결론 — 도구는 되돌릴 명령을 만들지 않는다. 만들 수 없기 때문이다.** 사실만 말한다:

```text
소비 state 가 커밋된 증거의 결속과 다릅니다 — 복구 창 안에서 state.json 이 바뀌었습니다.
  결속=… · 지금=…
  🔴 이 티켓에는 아무것도 쓰지 않았습니다 — 워킹 state 도 커밋도 그대로입니다.
  이 창에서 state 를 바꾼 작업(예: 정책 채택)을 **되돌린 뒤** 다시 실행하십시오.
  🔴 도구가 되돌릴 명령을 만들지 못합니다: 승인 시점 state 는 커밋되지 않아 그 바이트를 알 수 없습니다.
```

- 🔴 **왜 이것으로 충분한가**: 이 창에서 state 를 바꾼 것은 **사람이 한 일**이고(`req:repolicy --run`),
  무엇을 했는지 아는 것도 사람뿐이다. 도구가 모르는 것을 아는 척하는 것이 더 나쁘다.
- 🔴 **재발은 DEC-2 가 막는다.** 이 안내가 필요한 상황 자체를 만들지 않는 것이 본체이고, 이
  메시지는 **이미 그 상태가 된 저장소**를 위한 것이다.
- 🔴 **아무것도 쓰지 않았다는 사실을 말한다** — 그것이 사람이 다음 판단을 할 수 있게 하는 정보다.

## DEC-2 — 복구 창에서는 state 변경 verb 를 막는다 (결함 1)

대조만 넣으면 **막을 뿐 원인을 남긴다**. `req:repolicy` 가 그 창에서 checkpoint 를 커밋하는 것
자체가 잘못이다.

```ts
/** 복구 창인가 — **source 커밋 뒤·소비 전**. 근거는 `pending_evidence_for` 하나다. */
export function inRecoveryWindow(state): boolean
```

🔴 **`approval_evidence` 를 근거로 삼지 않는다**(phase-1 r01 P1). 승인 핀은 **승인 직후부터 소비까지**
살아 있는 **정상 상태**다. 그것으로 판정하면 승인만 받아 둔 티켓의 정책 채택이 통째로 막히고,
안내하는 `--finalize` 는 source 커밋이 없어 **완료할 수도 없다** — 새 교착이다.
결속이 존재할 수 있는 구간은 `pending_evidence_for` 가 가리키는 곳뿐이다.

- `req:repolicy --run` 이 이 창이면 **쓰지 않고 거부**한다. 안내: "먼저 `req:commit --finalize --run`
  으로 복구를 끝낸 뒤 다시 채택하십시오."
- 🔴 **dry-run 은 막지 않는다** — 무엇이 바뀔지 보는 것은 안전하고, 막으면 사람이 판단할 근거를
  잃는다.
- 🔴 **`req:repolicy` 만 막는다.** 지금 관측된 것이 그것 하나다. "state 를 쓰는 모든 verb" 로
  넓히면 `req:confirm`·`req:rebind` 까지 걸려 **새 교착**을 만든다 — 근거 없이 넓히지 않는다.
  (다른 verb 가 같은 문제를 내면 그때 같은 술어를 쓴다. 술어를 **공유 가능한 형태로** 둔다.)

## DEC-3 — `.gitignore` **완화·삭제**는 자동 안내하지 않는다 (결함 2)

`.gitignore` 의 dirty 상태는 두 종류이고 **반대 방향**이다.

| 종류 | stash 가 하는 일 | 안내 |
|---|---|---|
| 규칙 **추가**(ignored 가 늘어남) | 규칙이 사라져 파일이 드러난다 | 커밋하면 해결 ✅ |
| 규칙 **삭제·완화**(ignored 가 줄어듦) | 규칙이 돌아와 파일이 감춰진다 | 커밋하면 **노출이 영구화** ❌ |

### 🔴 `git status --porcelain` 이 비어야 한다는 검증은 **쓰면 안 된다** (설계 r01 P1)

초안은 커밋 뒤 `git status --porcelain` 이 비어 있어야 다음으로 간다고 했다. **그것은 정상 경로를
막는다** — 이 안내가 나오는 상황은 정의상 **옮길 작업이 남아 있는** 상태다(staged `code.ts`,
untracked `notes.txt`). REQ-2026-152 의 e2e 가 바로 그 fixture 를 쓴다. 게다가 삭제 경우에는
`stash -u` 가 노출된 파일까지 가져가므로 **그 시점 status 는 오히려 비어 있다** — 검증이
잡지도 못한다(실측: 노출은 `stash pop` **뒤**에 드러난다).

### 판정 — 커버리지가 **줄어들 수 있는가**만 본다

필요한 성질은 하나다: **HEAD 가 ignore 하던 것을 워킹 규칙도 여전히 ignore 하는가.**

🔴 **줄 집합(set) 비교로는 부족하다**(설계 r02 P1). gitignore 는 **마지막에 일치한 패턴이 이긴다** —
같은 두 줄이라도 순서가 바뀌면 커버리지가 줄어든다:

```
HEAD:  !keep.log      →  *.log       ⇒ keep.log 는 ignored(마지막 일치가 *.log)
워킹:  *.log          →  !keep.log   ⇒ keep.log 가 드러난다
```

집합에는 삭제도 새 `!` 도 없다. 그래서 판정은 **순서에 민감해야 한다.**

### 안전 조건(보수적 충분조건)

`.gitignore` 하나가 **안전**한 것은 다음이 **모두** 성립할 때뿐이다:

1. 워킹에 그 파일이 **존재**한다(삭제 아님).
2. HEAD 버전의 줄들이 워킹 줄들의 **순서를 보존한 부분수열**로 그대로 나타난다
   (HEAD 에 없던 파일이면 HEAD 줄이 비어 있으므로 자동 성립).
3. 그 부분수열에 속하지 않는 **삽입된 줄이 전부 비-부정**이다(`!` 로 시작하지 않는다).

**왜 충분한가**: HEAD 가 ignore 하던 경로 P 를 보자. HEAD 에서 P 에 마지막으로 일치한 줄 L 은
비-부정이다. 워킹에서 L 뒤에 오는 줄은 ① HEAD 의 L 이후 줄들(순서 그대로)과 ② 삽입된 비-부정
줄들뿐이다. ②는 P 를 **다시 ignore 하기만** 하고, ①은 HEAD 에서와 같은 결과를 낸다. 따라서 P 에
마지막으로 일치하는 줄은 여전히 비-부정 — P 는 계속 ignored 다. ∎

- 🔴 **패턴 의미를 해석하지 않는다.** 줄이 무엇을 매치하는지는 보지 않고, **순서와 부정 여부만**
  본다. gitignore 문법(와일드카드·`**`·디렉터리 접미)을 재구현하지 않는다.
- 🔴 **신규 untracked `.gitignore` 도 조건 3 을 받는다.** 하위 디렉터리에 `!keep.log` 만 든 새
  파일을 만들면 부모 규칙을 **부정**한다 — "신규 파일 = 순수 추가"는 틀렸다.
- 🔴 비교는 **줄바꿈을 정규화**해서 한다(CRLF/LF). 내용을 바꾸지는 않는다.
- 🔴 **초안의 "도구는 판정하지 않는다"를 뒤집는다.** 판정하지 않으면 도구가 사람의 미커밋 결정을
  대신 확정해 버린다(결함 2 의 본질). 다만 **판정의 출력은 "자동 명령을 낼지 말지"뿐**이고,
  무엇을 할지는 여전히 사람이 정한다. **애매하면 멈춘다.**

### 좁아질 수 있으면 자동 명령을 내지 않는다

```text
  🔴 미커밋 .gitignore 가 ignore 범위를 **좁힐 수 있습니다** — 이 변경을 도구가 대신 커밋하지 않습니다:
       .gitignore
     그대로 커밋하면 그 완화가 새 티켓 브랜치에 **영구히** 남고, 감춰져 있던 파일이 드러나
     다음 리뷰가 D10 에서 막힙니다. 규칙을 되돌릴지, 드러난 파일을 정리할지 **직접** 정하십시오.
     정한 뒤 방금 실행한 req:commit 명령을 다시 실행하면 이어지는 절차를 안내합니다.
```

- 🔴 **명령열 전체를 내지 않는다** — REQ-2026-152 phase-1 r03 과 같은 계약(반쪽 명령열 금지).
- 🔴 **순수 추가 경우는 종전 그대로** 자동 명령을 낸다. REQ-2026-152 의 e2e 2건(루트·중첩)이
  **끝까지 성공**하는 것이 이 phase 의 무회귀 오라클이다.

## DEC-4 — `splitDirty` 는 git 이 준 경로를 그대로 쓴다 (결함 3)

```ts
// 지금: paths = …map((p) => p.replace(/\\/g, '/'))   ← git 경로를 바꾼다
// 이후: paths = …                                     ← 그대로
```

- 🔴 `-z` porcelain 이 준 경로가 **정본**이다. POSIX 에서 역슬래시는 파일명의 일부다.
- 🔴 `ticketRel` 쪽의 `.replace()` 도 뺀다 — 입력은 `toTicketRel` 이 만든 POSIX 값이라는 것이
  이미 계약이고(REQ-2026-153 주석), 방어적 변환을 남기면 계약이 흐려진다.
- 🔴 **Windows 무회귀**: git 은 플랫폼과 무관하게 `/` 로 보고한다 — 변환은 처음부터 불필요했다.
