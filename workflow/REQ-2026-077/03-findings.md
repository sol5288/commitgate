## 증거

### ① 테스트가 시작조차 못 했다

교착한 두 잡의 `vitest.log`가 **104바이트**뿐이고 내용이 배너 한 줄이다.

```
 RUN  v2.1.9 /Users/runner/work/commitgate/commitgate
```

→ 🔴 **`init.test.ts` 내부의 어떤 테스트가 멈춘 것이 아니다.** vitest가 워커를 띄우고
테스트를 수집하는 **기동 단계**에서 멈춘다. 용의자 지목("init.test.ts가 무거워서")은
**대상은 맞았지만 이유는 틀렸다** — 이 파일이 지목된 것은 전체 스위트에서 마지막까지
등장하지 않았기 때문인데, 실제로는 그 파일이 **시작되지 못한** 것이다.

### ② 프로세스 트리 (두 인스턴스 동일)

```
node (vitest)            ← 본체
├── esbuild --service=0.21.5 --ping
└── node (vitest 1)      ← 워커
```

### ③ 스택 (`sample`, 1ms 간격)

| 프로세스 | 상태 | 샘플 |
|---|---|---|
| vitest 본체 | `uv__io_poll` → **`kevent`** — 오지 않는 것을 기다린다 | 1606/1607 · 1993/1996 |
| esbuild 서비스 | **`kevent`** — 놀고 있다 | — |
| **vitest 워커** | 🔴 **JS 안에서 회전** — `RunMicrotasks` → `PromiseFulfillReactionJob` → `AsyncFunctionAwaitResolveClosure` → 인터프리터 프레임 → `Builtins_ArrayFilter` | **1560/1560 · 1584** |

→ 본체는 **대기**, 워커는 **CPU를 태우는 루프**. 워커가 응답하지 않으니 본체가 영원히 기다린다.

### 🔴 앞선 가설 정정 — esbuild는 원인이 아니다

2026-07-27 CI 로그의 `Terminate orphan process: pid (2040) (esbuild)`를 보고
**"esbuild 고아 프로세스가 원인"**이라고 적었는데, **틀렸다.**
샘플에서 esbuild는 두 인스턴스 모두 `kevent`에서 **놀고 있었다** — 교착의 **피해자**(부모가
안 죽으니 남은 고아)이지 원인이 아니다. 원인은 **vitest 워커의 JS 루프**다.

### ④ 병렬 설정과 무관하다는 것의 재확인

프로브는 **파일 하나**를 돌린다 — 파일 병렬이 개입할 여지가 없다.
그런데도 교착이 난다. REQ-2026-044(전면 직렬)·REQ-2026-075(`maxWorkers: 2`) 어느 쪽도
이 현상의 원인이 아니었음이 이것으로 확정된다.

## 원인 (특정된 범위)

**vitest 2.1.9의 워커 기동 경로가 macOS arm64 + Node 18에서 약 20% 확률로 JS 루프에 빠진다.**

🔴 **더 좁히지 못한 것**: 회전 중인 JS 프레임이 JIT 코드라 심볼이 없다(`??? in <unknown binary>`).
어느 함수인지 이름으로 지목하려면 추가 계측(`--perf-basic-prof` 등)이 필요하다 —
이번 관측 범위 밖이며, **아래 권고를 먼저 시도하는 편이 비용이 낮다.**

## 조치 권고

### 권고 1 (우선) — vitest 업그레이드

- **왜 이 원인을 막나**: 교착이 **테스트 코드가 아니라 vitest 기동 경로**에서 난다.
  우리 코드에 손댈 지점이 없고, 2.1.9는 이미 오래된 버전이다.
- **어떻게 검증하나**: 🔴 **프로브가 측정 도구가 됐다.** 업그레이드 후 같은 조건으로 돌려
  교착률을 비교한다.
- ⚠️ **표본 크기 주의**: 관측 기저율 20%를 그대로 쓰면, 교착이 그대로인데도 **우연히 0건**이 나올 확률은

  | 실행 횟수 | 우연히 0건일 확률 |
  |---|---|
  | 10회 | **10.7%** |
  | 20회 | 1.15% |
  | 30회 | **0.124%** |
  | **31회** | **0.099%** (여기서 처음 0.1% 미만) |

  🔴 **10회로 판정하면 안 된다** — 10번에 한 번은 아무것도 안 고쳐도 0건이 나온다.
  "0.1% 미만"이라는 기준을 쓰려면 **31회 이상**이어야 한다. 30회는 0.124%다.
  (기저율 20%는 **10회 관측 2건**에서 나온 값이라 그 자체가 넓은 구간을 갖는다 —
  이 계산은 판정선을 정하는 근사이지 정밀한 신뢰구간이 아니다.)

### 권고 2 (대안) — 매트릭스에서 Node 18 제외

- **왜 이 원인을 막나**: 관측된 교착은 node 18에서만 났다(같은 커밋의 node 20·22는 매번 통과).
  Node 18은 **2025-04 EOL**이다.
- 🔴 **이것은 지원 범위 축소다 — 사용자 결정 사항이다.** `package.json`의 `engines`와
  문서가 약속하는 지원 범위를 함께 바꿔야 하고, required checks 이름도 바뀐다.
  도구가 임의로 줄이지 않는다.

### 기각한 대안

- **`pool`/`poolOptions` 변경** — 어느 함수가 도는지 모르는 상태에서의 추측이다.
  권고 1이 실패한 뒤에 근거를 갖고 볼 일이다.
- **`init.test.ts` 손보기** — 그 파일 **내용과 무관**하다(테스트가 시작조차 못 했다).
- **재시도(retry)로 덮기** — 교착은 실패가 아니라 **멈춤**이라 재시도가 발동하지 않는다.
  REQ-2026-076의 타임아웃이 있어야 실패로 바뀌고, 그때 비로소 재시도가 의미를 갖는다.
