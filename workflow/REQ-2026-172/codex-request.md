# REQ-2026-172 리뷰 요청

## 배경

`req:delegate` 가 발급 시점에 **아무것도 검증하지 않아** 거부 사유를 `integrate` 에서야 알게 된다.
소비자 실측에서 REQ 1개당 사람 승인 문장이 **1.54회**였고, 초과분의 상당수가
*발급 → 실패 → 철회 → 재발급* 이었다(철회 사유에 그대로 남아 있다).

## 변경 요약

발급 전에 **후보 행을 만들어 `delegationVerdict` 를 그대로 돌린다.** 거부 사유를
"지금 참 / 발급 시점에 성립 불가 / 요청에 달림" 으로 분류해, **지금 참인 것만** 발급을 막는다.
공유 코드 두 개(`collectDeepInput`·`readTicketFacts`)를 lib 으로 내린다.

## 리뷰 포인트

1. 🔴 **DEC-2 의 분류가 옳은가.** 특히 `trunk-moved` 를 "발급 시점에 성립 불가"로 둔 것 —
   발급 순간의 trunk 는 늘 현재이므로 그것으로 막으면 정상 발급이 전부 거부된다고 판단했다.
   `composition-changed`·`ledger-corrupt`·`ambiguous-active` 를 "지금 참"에 넣은 것도 봐 달라.
   **분류가 틀리면 결과는 둘 중 하나다: 과잉 차단(정상 발급 불가) 또는 무용지물.**

2. **게이트가 약해지지 않는가.** preflight 가 통과한 뒤 `integrate` 가 같은 판정을 다시 한다는 전제로
   설계했다. 발급 시점에 통과했다는 사실이 통합 시점 검사를 **어떤 경로로도** 대신하지 않는지.

3. **DEC-1 이 실제로 같은 술어인가.** 후보 행을 원장 텍스트에 이어 붙여 `delegationVerdict` 를 부르는데,
   그 구성이 실제 발급 후 상태와 **바이트/의미상 동일**한지. 다르면 "발급은 통과, 통합은 거부"가 남는다.

4. **DEC-4 의 안내가 실행 가능한가.** 플래그로 열리는 사유와 열리지 않는 사유를 갈랐는데,
   열리지 않는 것에 명령을 붙이지 않았는지. 그리고 `--sentence` 자리표시자가 **승인 문장을 지어내는**
   방향으로 새지 않는지.

5. **phase-1 재배치가 정말 동작 변경 0 인가.** `collectDeepInput`·`readTicketFacts` 가 옮겨지면서
   import 순환·초기화 순서·re-export 로 인한 타입 변화가 없는지.

6. **phase 분해가 옳은가.** 재배치(1)와 판정(2)을 나눈 것이 리뷰 면적상 이득인지,
   아니면 쓰이지 않는 이동을 한 라운드 리뷰하는 낭비인지.
