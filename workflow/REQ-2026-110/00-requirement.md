# REQ-2026-110 요구사항

doctor가 HIGH 확인 차단을 미리 알린다

## 배경

2026-08-02 자체 감사 B트랙 4번째. 감사가 **X-6(진단 공백)**으로 분류한 항목이다.

### 실측된 공백

`req:commit`의 차단 게이트 21개를 doctor의 D-체크와 대조한 결과, **정확히 하나만 doctor에 대응이 없다.**

| 커밋 게이트 | doctor 대응 |
|---|---|
| setup 완료 | D24 |
| `commit_allowed` | D6 |
| `approval_evidence` | D16 |
| staged tree == `approved_diff_hash` | D9 |
| 증거 아카이브 정합 | D16/D17 |
| clean tree | D10 |
| design 선행 | D13 |
| **HIGH 사람확인(`userConfirmGate`)** | **없음** |

즉 HIGH 티켓에서 확인 기록이 없거나 scope가 어긋나면 **`req:doctor`는 PASS를 내는데 `req:commit`은 실패한다.** 사용자는 doctor를 통과시켜 놓고 커밋에서 막히며, 왜 막혔는지는 커밋을 실행해봐야 안다.

### 왜 이것이 값어치 있나

원장 실측(REQ-2026-100 조사)에서 티켓 소요 시간의 **86~91%가 리뷰 라운드 사이**, 즉 사람과 빌더가 상태를 파악하고 조치하는 구간이었다. Codex 왕복은 9~14%다. **막힌 이유를 미리 알려주는 것이 리드타임에 직접 작용한다** — 이 감사에서 D18 오탐 제거(REQ-107)와 함께 지목한 두 지렛대 중 하나다.

## 요구

1. **`req:doctor`가 HIGH 확인 차단을 WARN으로 알린다.** 새 체크 **D28**을 만든다.
   - 🔴 **절대 FAIL이 아니다.** `req:commit`이 doctor를 하드 게이트로 spawn하므로 FAIL이면 같은 조건을 두 번 막는 셈이고, doctor 쪽 판정이 조금이라도 어긋나면 커밋이 **doctor 때문에** 막힌다. D19~D27이 전부 WARN 상한인 이유와 같다.
   - 진단은 **차단하는 게이트를 복제하지 않는다.** 실제 차단은 계속 `req:commit`의 `userConfirmGate`가 한다.

2. **판정을 공유한다.** D28은 `userConfirmGate`(정본)를 호출한다. REQ-2026-107에서 D18이 리뷰 게이트와 갈라져 오탐을 냈던 것과 같은 실패를 만들지 않는다.

3. **차단 사유를 그대로 전달한다.** `userConfirmGate`가 이미 조치 명령(`req:confirm … --scope …`)을 포함한 사유 문자열을 만든다. 그것을 재작성하지 않고 전달한다 — 두 표면이 다른 문구를 내면 어느 쪽이 맞는지 사람이 판단해야 한다.

## 비요구

- **`req:commit` 쪽 변경**: 실제 차단은 그대로 둔다. 이 REQ는 **보이게** 만들 뿐이다.
- **doctor 체크 병합(21→10)**: 감사가 제안한 마지막 항목. 별도 판단(아래 참고).

## 완료 기준

- HIGH + 확인 없음 → D28 **WARN**이고 사유에 `req:confirm` 조치가 들어 있다.
- HIGH + 유효 확인 → D28 **OK**. LOW → D28 OK(해당 없음).
- **FAIL은 어떤 입력에서도 나오지 않는다**(exit code 불변).
- `D_CHECK_IDS`·정본 표(`07 §3`)에 D28이 함께 등재된다(집합 동일성 테스트 통과).
