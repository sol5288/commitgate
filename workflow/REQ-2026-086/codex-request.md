# REQ-2026-086 리뷰 요청

## 배경

소비 repo(yammy) 0.11.0 구간 감사의 마지막 항목. phase 26개 중 **18개(69%)가 granularity 권고치(8파일)를
초과**했고, 초과 phase의 평균 리뷰 라운드는 **2.39**(≤8파일은 1.38)였다. D18은 매번 WARN을 냈고 매번 무시됐다.

무시되는 이유가 둘이다: (1) 무시에 비용이 0이고(`절대 FAIL 아님`), (2) **시점이 커밋 직전이라 이미 늦다** —
그때 "쪼개라"는 말은 이미 짠 코드를 되돌리라는 뜻이라 리뷰 한 번 더 받는 것보다 비싸다.

핵심 관찰: **리뷰 직전이라면 시정이 싸다.** 아끼려는 것이 리뷰 라운드이고, 그 시점의 시정은
코드 재작성이 아니라 `git restore --staged`(staging 재구성)다.

## 변경 요약

- **phase-1**: 판정을 phase 리뷰 실행 **직전**(예산 게이트·attempt 기록·pre-call 원장 커밋보다 앞)으로 옮기고, 초과 시 리뷰를 실행하지 않는다. 탈출구 둘: staging 축소 / `phases[]`에 `max_files` 선언. 되돌리는 설정 `granularityGate: 'warn'` 한 줄.
- **phase-2**: D18 문구(레벨은 WARN 유지)·문서·CHANGELOG.

## 리뷰 포인트

- 🔴 **차단 순서**: 판정이 `gateAndRecordAttempt`(예산·attempt)와 `precallCommitLedgerRow`(원장 커밋)보다 확실히 **앞**인가. 뒤면 attempt가 열리고 부기 커밋이 남은 뒤 막혀 "아무것도 소모하지 않는다"가 거짓이 된다.
- **교착 없음**: D18을 WARN으로 남긴 근거가 맞는가 — FAIL로 올리면 이미 승인받은 phase가 커밋되지 못하고 승인도 소비되지 않는 상태가 된다.
- **탈출구의 실효성**: 정당하게 큰 phase(기계적 일괄 변경)가 영영 막히지 않는가. `max_files` 선언이 `state.json`에 남아 **기록**되는가.
- **오라클 회피**: `02-plan.md`를 파싱하지 않는가(REQ-2026-041 폐기·044 DEC-7 교훈). `phases[]`가 이미 기계가 읽는 구조라는 전제가 맞는가.
- **파일 분류**: 리뷰 시점에 D10이 클린을 보장하므로 `git diff --cached --name-only` 중 티켓 디렉터리 밖 = 그 phase의 코드 변경, 이 전제가 맞는가. doctor의 분류를 복제하지 않은 것이 옳은가.
- **범위**: design 리뷰가 영향받지 않는가. `granularityMaxFiles` 기본값·D18 판정식이 안 바뀌었는가.
- ⚠️ **의도된 동작 축소**: 업그레이드 시 진행 중이던 큰 phase가 멈춘다. 이 tradeoff가 CHANGELOG에 충분히 고지되는가(phase-2).
