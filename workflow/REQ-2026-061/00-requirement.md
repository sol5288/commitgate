# REQ-2026-061 요구사항

commitgate check — 비대화형 진단 verb

## 배경

REQ-2026-060이 `commitgate setup`을 **대화형 전용**으로 만들면서, 리뷰어 CLI 가용성·인증 진단
(`versionProbe`/`authProbe`)이 **setup 내부에만** 존재하게 됐다. 그 REQ는 *"에이전트가 호출할 진단 표면을
만들지 않는다"* 를 명시적 비목표로 두고 끝냈다(REQ-2026-060 `00-requirement.md`).

그래서 지금은 **에이전트도 사람도 비대화형으로 상태를 확인할 방법이 없다**:
- 설정이 스키마에 맞는지 보려면 `req:doctor`를 돌려야 하는데, 그건 **활성 티켓**을 전제로 한다
  (`req:doctor <REQ>`). 티켓이 없는 시점(설치 직후·CI)에는 쓸 수 없다.
- codex 설치·로그인 여부는 여전히 첫 리뷰 호출에서야 드러난다. 그 실패는 `dispatched`로 분류되어
  **리뷰 예산을 차감**한다(`adapters.ts:190-192`).

## 요구사항

| # | 내용 |
|---|---|
| **R1** | `commitgate check` verb 신설 — **비대화형**. 에이전트·CI가 자유롭게 호출할 수 있다 |
| **R2** | `req.config.json` 유효성(파싱 + AJV) 진단 |
| **R3** | 리뷰어 CLI **설치**(`versionProbe`)·**로그인**(`authProbe`) 진단 |
| **R4** | 티켓이 **없어도** 동작한다 — 설치 직후 첫 확인 수단이어야 한다 |
| **R5** | 사람이 읽는 출력과 **기계가 읽는 출력**(`--json`)을 모두 낸다 |

## 🔴 비목표

| 비목표 | 이유 |
|---|---|
| **어떤 게이트에도 배선하지 않는다** | `req:commit`이 `req:doctor`를 하드 게이트로 spawn하는 것과 **다르다**. check는 어디서도 spawn되지 않으므로 exit code가 무엇이든 기존 워크플로를 막지 않는다. 배선은 REQ-F(리뷰 preflight)의 소관 |
| **아무것도 고치지 않는다** | 읽기 전용 진단이다. `--fix` 류를 만들지 않는다 — 수정은 `setup`(대화형)·`sync`·`quickstart`가 각자 담당한다 |
| **로그인을 실행하지 않는다** | 대화형이 필요하므로 `setup`의 소관이다. check는 **상태를 보고하고 명령을 안내**만 한다 |
| **setup 강제·stopGate·원장 기록** | 각각 후속 REQ |

## 수용 기준

1. 티켓이 하나도 없는 repo에서 `commitgate check`가 동작한다.
2. 설정이 깨졌거나 codex가 없거나 미로그인이면 **exit ≠ 0**이고, 무엇을 해야 하는지 출력한다.
3. 전부 정상이면 exit 0.
4. `--json`이 안정된 형태를 낸다(에이전트 소비용).
5. `authProbe`가 `unknown`이면 **실패로 단정하지 않는다** — 별도 상태로 보고한다.
6. `npm test` green · `tsc --noEmit` 0.
