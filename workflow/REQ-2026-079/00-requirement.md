# REQ-2026-079 요구사항 — macos node 18 교착을 없앤다 (vitest 실행 방식 변경)

## 근거

REQ-2026-077이 원인을 특정했다(`workflow/REQ-2026-077/03-findings.md`):

- 교착은 **테스트가 하나도 실행되기 전** vitest 기동 단계에서 난다(출력이 배너 한 줄뿐).
- 스택: 본체는 `kevent` 대기 · **워커가 JS 루프에서 회전**(1560/1560 샘플) · esbuild는 놀고 있다.
- 파일 하나만 돌려도 재현되므로 **우리 테스트 코드·병렬 설정과 무관**하다.
- 실측 재현율 **10회 중 2회(20%)**.

→ 손댈 지점이 vitest 자체뿐이다.

## 버전 실측 (2026-07-28)

| 버전 | engines(node) | 판단 |
|---|---|---|
| **`2.1.9`** (현재) | `^18 \|\| >=20` | 🔴 **이미 2.x 최신** — 같은 major 안에서 올릴 데가 없다 |
| **`3.2.7`** | `^18 \|\| ^20 \|\| >=22` | ✅ **Node 18을 유지하는 유일한 상위 경로** |
| `4.1.10` | `^20 \|\| ^22 \|\| >=24` | 🔴 **Node 18을 버린다** |

우리 `package.json`의 `engines`는 `>=18.17`이고 CI 매트릭스는 node 18·20·22다.
→ 🔴 **4.x는 지원 범위 축소를 강제**하므로 이번 범위가 아니다.

## 🔴 착수 후 근거 변경 — 업그레이드가 아니라 `pool` 변경이 1순위다

구현 중 실측이 계획을 바꿨다(상세는 설계 DEC-1):

| 조합 | 스위트 결과 |
|---|---|
| vitest 2.1.9 · forks(현행) | exit 0 |
| vitest 3.2.7 · forks | 🔴 **exit 1** — 워커 RPC 타임아웃 4건 |
| vitest 3.2.7 · threads | exit 0 |
| **vitest 2.1.9 · threads** | **exit 0** |

**업그레이드 없이 `pool: 'threads'`만으로 스위트가 깨끗하다.** 그리고 REQ-2026-077이 관측한 교착은
**워커 프로세스**에서 났는데(forks), threads에는 그 프로세스가 없다.

→ **변수를 하나만 바꾼다**: `pool: 'threads'`. 둘을 함께 바꾸면 고쳐져도 **어느 쪽이 고쳤는지 모른다.**

## 수용 기준

1. **전체 스위트가 green**이다(로컬 + CI 9잡). 🔴 **교착 판정에 작용하는 변수는 `pool` 하나**다 —
   고쳐졌을 때 **무엇이 고쳤는지 말할 수 있어야** 하기 때문이다.
   같은 커밋에 들어가는 `testTimeout`·`hookTimeout` 조정은 **판정의 변수가 아니다**:
   교착은 **테스트가 시작되기 전**에 나므로(교착 잡의 vitest 출력이 배너 한 줄뿐 — REQ-2026-077 실측)
   테스트당 상한은 적용될 대상이 없다. 이 계약은 phase-2에서 **재검증**한다(설계 DEC-4b).
   `package.json`·lockfile은 **건드리지 않는다**(vitest `^2.1.2` 유지).
2. `engines: >=18.17`과 CI 매트릭스(node 18·20·22)를 **바꾸지 않는다.** 지원 범위는 이 REQ의 범위 밖이다.
3. 🔴 **프로브 31회 이상으로 검증한다.** 기저율 20%에서 아무것도 고치지 않아도 우연히 0건이 나올 확률이
   10회 **10.7%** · 30회 **0.124%** · **31회 0.099%**다. 10회로 판정하지 않는다.
4. 🔴 **고쳐지지 않아도 그 사실을 기록하고 끝낸다.** 교착이 남으면 남은 선택지
   (vitest 3 + threads · Node 18 제외 = **지원 범위 축소 = 사용자 결정**)를 findings에 정리한다.
   안 고쳐진 것을 고쳐졌다고 하지 않는다.
5. 스위트 소요가 크게 나빠지지 않는다(현재 로컬 290초 · CI 최장 windows 7.7분).

## 범위 밖

- **Node 18 지원 중단** — 지원 범위 축소라 사용자 결정 사항이다.
- vitest 4 — 위와 같은 이유.
- 테스트 코드 리팩터링(스폰 → `main()` 직접 호출) — 별개의 큰 작업이며 이 교착의 원인도 아니다.
