# REQ-2026-173 요구사항

## 무엇

사전 위임의 `trunk-moved` 거부를 **"trunk 가 움직였다"**에서
**"trunk 가 인가되지 않은 방식으로 움직였다"**로 좁힌다.

trunk 에 더해진 커밋이 **전부 이 원장이 인가한 병합**이면 위임을 그대로 유효하게 둔다.
하나라도 그 밖의 것이 있으면 지금처럼 거부한다.

## 왜 (관측된 사실)

`lib/delegation.ts` 의 `delegationVerdict`:

```ts
if (row.trunk_sha !== input.trunkSha)
  return deny('trunk-moved', `위임 발급 이후 ${row.trunk_branch} 가 움직였다(…)`)
```

**SHA 가 다르기만 하면 거부**한다. 그래서 REQ 를 여러 개 끝내 놓고 차례로 통합하면,
**앞 REQ 를 병합하는 순간 뒤 REQ 들의 위임이 전부 무효**가 된다.

소비자 저장소 `44_meallo` 의 원장에 그대로 남아 있다:

```
2026-08-21T16:53:40  REQ-296  trunk 4897df8b   ┐ 세 건을 같은 기준선에서 한 번에 발급
2026-08-21T16:53:52  REQ-297  trunk 4897df8b   │
2026-08-21T16:54:08  REQ-298  trunk 4897df8b   ┘
2026-08-21T17:47:35  REQ-296  trunk 4897df8b   ┐ 한 시간 뒤 순차 통합 → 전부 재발급
2026-08-21T17:48:04  REQ-297  trunk 3bdbc211   │
2026-08-21T17:48:52  REQ-298  trunk 3139dc12   ┘
```

철회 사유가 사실을 말한다: *"287 통합으로 trunk 기준선 이동(1ad8a5fd→91a96b8b) — **같은 승인으로** 재발급"*.
**같은 승인인데 문장을 다시 받고 있다.**

| 항목 | 값 |
|---|---|
| meallo 초과 발급(재발급) 총계 | 29 |
| 그중 `trunk-moved` 연쇄로 설명되는 것 | **9 (31%)** |

🔴 이 저장소에서도 방금 겪었다 — REQ-169 를 통합하자 REQ-170 의 통합에 위임을 새로 발급해야 했다.

## 핵심 논지

**사람이 승인한 것은 "무엇을 병합해도 되는가"이지 "main 이 어느 SHA 에 있는가"가 아니다.**
기준선 재고정은 **부기**이고, 범위·권한의 확대는 **결정**이다.
지금 코드는 그 둘을 같은 값(`trunk_sha`)으로 취급한다.

## 완료 기준

1. `trunk_sha` 가 달라도, 그 사이에 더해진 커밋이 **전부 이 원장이 인가한 병합과 그 부기**이면 통과한다.
2. 🔴 하나라도 그 밖의 것(손으로 민 커밋·미입증·손상 증거·**다른 원장의 병합**)이 있으면 **거부**한다.
   판정 불가도 거부다 — 모르면 막는다(통합은 차단 지점이다).
3. 🔴 **인가 판정은 원장이 근거**다. 설정값·브랜치 이름·시각으로 열리지 않는다.
4. 통과한 경우 그 사실이 **보고와 원장에 남는다** — "trunk 가 움직였지만 인가된 병합뿐이었다"를
   조용히 넘기지 않는다.
5. 기존 거부는 그대로 — 인가를 판정할 **입력이 없으면** 종전대로 `trunk-moved` 로 거부한다(무회귀).

## 비목표

- 위임의 **범위·권한** 완화. 바뀌는 것은 `trunk_sha` 축 하나뿐이고, scope·HIGH·evidence·만료는 그대로다.
- 만료(`expires_at`) 연장. 시간 축은 이 REQ 가 건드리지 않는다.
- `req:delegate --rebase` 같은 **재발급 명령** 추가. 재고정이 필요 없게 만드는 것이 이 REQ 다.
