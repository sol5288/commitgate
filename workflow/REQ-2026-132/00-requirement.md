# REQ-2026-132 요구사항

## 무엇

리뷰 **소프트 예산**(`autoBudget`) 소진 시의 처리를 설정으로 고를 수 있게 한다.

```jsonc
"reviewBudget": { "autoBudget": 5, "hardCap": 8, "onSoftLimit": "ask" }
//                                              "ask"(기본·현행) | "auto"
```

- `ask`(기본): 현행 그대로 — 6~8회차는 매 회차 `req:review-exception` 사람 승인이 필요하다.
- `auto`: 사람 승인 없이 `hardCap`까지 진행하되, **정책으로 진행했다는 사실을 원장에 남긴다**.

🔴 **`hardCap`(절대 호출 상한)은 어느 값에서도 그대로다.**

## 왜

`stopGate`를 `req`·`merge`로 두고 계약이 자율 진행을 규정해도(REQ-2026-131), **리뷰가 5회를 넘는
순간 워크플로가 매 회차 멈춘다.** 그 정지는 `stopGate`가 정한 것이 아니라 예산 축이 따로 만든 것이라,
사용자가 고른 정지 지점과 무관하게 끼어든다 — 사용자가 관찰한 "케이스마다 다르게 끊긴다"의 한 축이다.

그런데 6~8회차의 사람 승인은 **비용 통제**가 목적이지 안전 게이트가 아니다:

- 승인 문장이 무엇을 보증하지 않는다 — "한 번 더 돌려도 된다"는 예산 판단이다.
- 실제 상한(`hardCap`)은 따로 있고 그것은 어떤 경로로도 뚫리지 않는다.

즉 이 정지는 **끄고 켤 수 있어야 하는 종류**인데 현재는 강제다.

## 제약

- 🔴 **기본값은 `ask`**(현행 무회귀). 비용이 드는 축의 기본을 조용히 바꾸지 않는다.
- 🔴 **`hardCap` 불변.** `auto`는 "무한 재시도"가 아니라 "6~8회차의 사람 확인 생략"이다.
- 🔴 **기록을 잃지 않는다.** `ask`에서 남던 예외 기록 자리에 `auto`는 **정책 근거 행**을 남긴다 —
  "왜 6회차가 나갔는가"에 대한 답이 원장에서 사라지면 안 된다.
- 🔴 **사람 승인을 위조하지 않는다.** `auto`는 `review_exception_confirmed`를 만들지 않는다.
  기록의 종류가 다르다(정책 vs 사람).
- 🔴 resume·세션 유지 재리뷰는 **범위 밖**이다(REQ-2026-045에서 감사 붕괴·drift 재발 이유로 확정 제외).

## 완료 기준

- `reviewBudget.onSoftLimit`가 스키마·config에 있고 기본이 `ask`다.
- `ask`: 현행과 **동일**(6회차에 예외 없으면 throw).
- `auto`: 6~8회차가 예외 없이 진행되고, 원장 행에 **정책으로 진행했다는 사실**이 남는다.
- 두 값 모두 9회차(`dispatched >= hardCap`)는 **차단**된다.
- `req:next`의 예산 안내가 `onSoftLimit`에 따라 갈린다(`auto`면 "사람 결정 필요"라고 말하지 않는다).
- `req:review-exception`이 `auto` 설정에서 **예외를 부여하지 않는다**(부여하면 도구가 스스로 "auto는
  사람 승인을 만들지 않는다"를 어긴다).
- 기존 부분 설정 `{"reviewBudget":{"autoBudget":3,"hardCap":6}}`이 업그레이드 후에도 **그대로 유효**하고
  `onSoftLimit`는 `ask`로 채워진다.
