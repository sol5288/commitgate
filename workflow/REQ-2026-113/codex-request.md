# REQ-2026-113 리뷰 요청

## 배경

델타 리뷰의 전면 재리뷰 escalation(`full_review_requested: "yes"`)이 **실측 0회**다.
소비자 3개 저장소 전수 조사(271티켓·리뷰호출 2,089건·16일) 결과:

| 항목 | 값 |
|---|---:|
| design 리뷰 호출 | 955 |
| **그중 델타 모드** | **241 (25.2%)** |
| escalation 발화 | **0** |

델타 모드는 `hasDesignBaseline`일 때만 켜지고 baseline은 **design 승인 분기에서만** 저장되므로,
escalation을 쓸 기회가 있었던 것은 2,024가 아니라 **241회**다.
(이 수치는 `applyDeltaPersona(base, true)`의 `policy_version` 해시를 **역산**해 얻었다 —
로그에 델타 여부가 없기 때문이다.)

## 이 REQ가 **하지 않는 것**과 그 이유

착수 전 조사에서 두 가지를 확인했고, 그 결과 **원안(지침 추가)을 폐기**했다.

1. **발화 지침은 이미 있다** — `DESIGN_DELTA_CONTRACT`의 마지막 줄(`review-codex.ts:470`)이
   언제 escalate할지 명시한다(REQ-2026-035가 넣음). "지침이 없어서"라는 진단이 틀렸다.
2. **문맥 부족을 호소한 흔적이 없다** — design 아카이브 902건을 훑었으나 실제 사례 0건.

원인 후보가 하나 더 있다 — **비용 비대칭**. escalation은 `commit_approved: "no"`를 강제하고
baseline을 삭제해 다음 라운드를 전체 재리뷰로 만든다. 판단할 수 있는 리뷰어는 그냥 판단한다.

**지식 문제인지 비용 문제인지 모르므로 지침을 늘리지 않는다.** 대신 **셀 수 있게 만들고
사실을 기록한다.** 원인 규명은 명시적 비목표다.

## 배선 위험을 **구조로** 제거한 부분 (중점 검토 요청)

이 저장소는 "빌더 직접호출 가드는 배선끊김을 못 잡는다"를 세 번 실증했고, 보통은 실제 진입점을 돌린다.
**여기서는 유료 codex 호출이 필요해 그럴 수 없다.** 대신:

| 필드 | 배선 위험 | 제거 방법 |
|---|---|---|
| `full_review_requested` | **없음** | 빌더가 **이미 받는** `verdict`에서 파생 — 넘길 인자가 없다 |
| `delta_mode` | 인자 1개 | 빌더 인자를 **필수**(`deltaMode: boolean`)로 두어 호출부 누락이 **컴파일 오류** |

행 필드는 둘 다 **선택**(`?`)이다 — 이미 쌓인 2,089행에 이 필드가 없기 때문이다.
빌더 인자는 필수, 행 필드는 선택 — 이 비대칭이 의도한 설계다.

**남는 한계를 명시한다**: 호출부가 `deltaMode`에 잘못된 값(상수 `false` 등)을 넘기는 경우는
타입이 못 잡는다.

## 리뷰 포인트

1. **배선 위험 제거가 충분한가.** 위 두 구조가 "조용한 미배선"을 실제로 막는지,
   아니면 그래도 e2e 오라클이 필요한지(그 경우 유료 호출 없이 어떻게 할지 제안 요청).
2. **`full_review_requested`를 boolean으로 정규화한 것.** 스키마는 `"yes"`/`"no"` 문자열이고
   선택 필드라 부재가 흔하다. `=== 'yes'`가 아닌 모든 값을 `false`로 접었는데(요청을 과대계상하지
   않는 방향), 세 상태를 구별할 이유가 있는지.
3. **행 필드는 선택 / 빌더 인자는 필수**라는 비대칭이 맞는지.
4. **gaps 정정 방식** — 삭제가 아니라 해소 표기(G-06 선례). 기존 서술을 이력으로 남기는 것이
   맞는지, 아니면 오해를 부르는지.
5. **원인 규명을 비목표로 둔 것.** 데이터를 먼저 모으는 순서가 맞는지.
