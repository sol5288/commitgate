# REQ-2026-112 리뷰 요청

## 배경

REQ-2026-071이 HIGH 티켓의 "매 phase 사람 확인" 백스톱을 **의도적으로 제거**하고 정지 지점을
`stopGate`가 단독으로 정하게 바꿨다. REQ-2026-073이 그때 문서 5곳을 정정하고 회귀 가드를 만들었다.

**그 정정이 `README` + `docs/`에만 적용됐다.** 같은 주장이 6곳에 살아 있다:

- `bin/setup.ts:230` — 🔴 **setup 마법사가 `stopGate` 값을 물을 때 화면에 띄우는 고지**
- `AGENTS.template.md:77` — `init`이 소비자 `AGENTS.md`로 복사하는 계약 템플릿
- `docs/ssot-design/04:54` — **가드 범위 안인데 표현이 달라 통과했다**
- `scripts/req/lib/config.ts` 39·53·214 — 주석

실제 동작은 `req-commit.ts:132~133`이다 — `merge`면 커밋에서 안 막고, `req`(기본값)면 REQ를 완성시키는
커밋에서만 막는다. 즉 **기본 설정에서 이미 거짓**이다.

## 이번 라운드(design r03)에서 고친 것 — r02 P1 1건

**지적**: 전수 발화 오라클은 **사본이 정본보다 적을 때만** 잡는다. 내용이 같은 배열 사본은
그대로 통과하므로 "목록이 한 곳"이라는 AC-7이 보장되지 않는다. — **맞는 지적이다.**

→ **구조로 먼저 막는다.** 매칭을 정본 모듈이 소유하게 하고(`retiredClaimsIn`),
`req-doctor.ts`는 **배열을 import하지 않는다.** 함수만 가져가 재수출한다.
배열을 손에 쥐지 않으면 **사본을 둘 자리가 없다.**

그 위에 오라클 두 겹:
- **AC-7a 참조 동일성** — 재수출된 함수가 정본과 `toBe` 같은 객체인가.
  **내용이 같은 사본 구현도 여기서 실패한다**(r02가 지적한 바로 그 시나리오).
- **AC-7b 행동 전수** — `main()`을 통해 정본의 모든 항목이 발화하는가(배선 보장).

🔴 **남는 한계를 설계에 명시했다**(DEC-4 말미): 재수출은 해 놓고 `main()` 안에서 사설 재구현을
호출하는 코드는 이론적으로 가능하다. 그러려면 재수출 함수를 **죽은 코드**로 두어야 하고,
두 목록이 어긋나는 순간 AC-7b가 실패한다. 이 잔여 위험을 없애려면 소스 정규식이 필요한데
이 저장소는 그 길을 두 번 폐기했다(REQ-2026-099) — 그래서 **감수하고 명시**한다.

## 이전 라운드(design r02)에서 고친 것 — r01 P1 2건

**P1-1 (오라클 공백: 코드 주석 4곳 미검사)**
원안은 배포 문서 표면과 `STOP_GATE_HIGH_NOTICE` 값만 검사해서, `scripts/req/lib/config.ts`의 주석 3곳과
`bin/setup.ts`의 근거 주석을 옛 주장 그대로 남겨도 전 검증이 통과했다. **6곳 정정을 요구하면서
4곳에 오라클이 없었다.**

→ AC-1을 **AC-1a(배포 지침 표면)** 와 **AC-1b(코드 표면)** 로 나눴다. AC-1b의 대상은
`bin/setup.ts` · `scripts/req/lib/config.ts`의 **명시적 파일 목록**이다.
🔴 `**/*.ts` 글로브가 아니다 — 그러면 폐기 문구를 설명하는 정정문까지 걸려 정정 자체가 막힌다.
그래서 **제외 목록**(등재 정본 모듈 · 가드 자신 · `CHANGELOG.md` · `workflow/REQ-*`)도 함께 명시하고
테스트가 두 목록을 다 단언한다.

**P1-2 (오라클 공백: 목록 이중화를 못 잡음)**
원안의 AC-7은 "테스트와 진단이 같은 모듈을 import"였는데, `req-doctor`가 **동일한 배열 사본**을
들고 있어도 통과했다. 이후 한쪽만 갱신되면 진단이 조용히 거짓이 된다.

→ AC-7의 오라클을 **행동**으로 바꿨다: **`RETIRED_CLAIMS`의 모든 항목**을 각각 `AGENTS.md`에 넣고
D29가 발화하는지 전수 확인한다. 정본에 항목을 추가했는데 진단이 못 잡으면 실패한다.
소스에서 `import` 문을 정규식으로 찾는 방법은 쓰지 않았다(REQ-2026-099의 교훈).

## 변경 요약

**Phase 1** — 6곳 정정 + 가드 범위 확장(배포되는 지침 파일 4표면) + 표현 변형 등재 +
`STOP_GATE_HIGH_NOTICE` **상수 직접 검증**.

**Phase 2** — 폐기 문구 목록을 배포 모듈 `scripts/req/lib/retired-claims.ts`로 정본화하고,
소비자 `AGENTS.md`에 남은 폐기 주장을 **새 진단 D29(WARN)** 로 알린다. 파일은 고치지 않는다.

## phase-1 r03에서 고친 것 — r02 P1

**지적**: 통합 승인 절도 `통합`이라는 **단어 존재만** 확인해서, 마지막 절을 `…필요하지 않습니다`로
뒤집어도 통과한다. — **맞는 지적이다.** r01과 같은 부류가 한 절 더 남아 있었다.

→ 긍정 의미를 단언하고 부정형을 금지한다:

```ts
expect(tail).toContain('어느 값에서도 필요')
expect(tail).not.toMatch(/필요\s*(하지\s*않|없)|불필요/)   // 어떤 형태로도 뒤집을 수 없다
```

**변이 검사로 확인**: 지적한 그대로 `필요하지 않습니다`로 바꾸니 해당 테스트가 실패했다.

ℹ️ 이 절에는 `userConfirmGate` 같은 **순수 판정 함수 앵커가 없다.** 통합 정지는 `req:next`가
종단에서 내는 `AWAIT_HUMAN`이라 커밋 게이트처럼 한 함수로 노출돼 있지 않다. 그래서 여기서는
문구 의미(긍정/부정)를 고정하는 데까지만 했다 — 더 강한 결속이 필요하다고 보시면 알려 주시기 바란다.

## phase-1 r02에서 고친 것 — r01 P1

**지적**: AC-2가 `phase`·`req`·`merge`·`통합`이라는 **단어 존재만** 확인해서, 두 값의 설명을
**서로 바꿔 놓아도 통과**한다. 사용자가 정반대를 안내받는데 게이트가 못 잡는다. — **맞는 지적이다.**

→ 값↔의미 매핑을 **실제 정지 규칙에 결속**했다. 먼저 `userConfirmGate`로 진짜 동작을 확인하고,
고지의 해당 절이 같은 말을 하는지 본다:

```ts
it('req — 중간 phase는 안 멈추고 REQ를 끝내는 커밋에서 멈춘다', () => {
  expect(userConfirmGate(high, 'req', false).blocked).toBe(false)  // 진짜 규칙
  expect(userConfirmGate(high, 'req', true).blocked).toBe(true)
  expect(seg('req')).toContain('REQ를 끝내는')                      // 고지가 같은 말을 하는가
})
```

**변이 검사로 확인**: 지적한 그대로 `phase`와 `req`의 설명을 교환하니 두 테스트가 실패했다.

부수 효과로 **역방향 결속**도 생겼다 — 나중에 `userConfirmGate`가 바뀌면 이 테스트가
"고지도 바꿔야 한다"고 알려준다. 사본을 두지 않고 정본 판정 함수를 그대로 import한다.

## 🔴 계획 대비 편차 — 파일 1개 추가 (phase-1)

`02-plan.md`의 Phase 1 범위는 **6파일**인데 staged는 **7파일**이다. 추가된 것은
**`tests/unit/setup.test.ts`** 이며, 이유는 다음과 같다.

그 파일의 두 테스트가 **옛 거짓 문구를 계약으로 고정**하고 있었다:

```ts
it('🔴 hint 가 HIGH 예외와 통합 승인 필요를 고지한다', () => {
  expect(h).toContain('HIGH')
  expect(h).toContain('매 phase 확인')   // ← 폐기된 보장을 단언
})
```

고지를 정정하는 순간 이 두 테스트가 실패한다. 즉 **정정과 분리할 수 없는 변경**이다.
계획을 쓸 때 이 의존을 예상하지 못했다(역의존 조사에서 `setup.test.ts`를 대상으로 잡아 놓고도
그 안의 단언 내용까지는 확인하지 않았다).

설계 문서를 고치면 승인 해시가 깨져 design 재승인이 필요하므로, **여기서 편차를 밝히고 판단을 구한다.**
scope 위반으로 보시면 반려해 주시면 계획을 고쳐 재승인받겠다.

> 부수 발견: **테스트 스위트가 거짓 서술을 고정하고 있었다.** 가드가 문서만 보고 테스트 단언은
> 보지 않으면, 정정을 시도할 때마다 스위트가 그것을 회귀로 신고한다.

## 리뷰 포인트

0. **r01 P1 2건이 실제로 닫혔는가.** (a) 이제 6곳 **전부**에 기계 검사가 걸리는가 —
   AC-1a(문서 4표면) + AC-1b(코드 2파일). (b) AC-7의 전수 발화 검사가 사본 드리프트를
   실제로 잡는가, 아니면 여전히 빠져나갈 구멍이 있는가.

1. **고지 새 문구가 실제 동작과 정확히 일치하는가** (DEC-1).
   `phase`=매 phase 커밋 전 · `req`=REQ를 끝내는 커밋 전 · `merge`=커밋에서는 안 멈춤 ·
   통합 승인은 어느 값에서도 필요. 특히 **둘째 절을 참이라고 판단해 유지**한 것이 맞는지.

2. **가드 범위를 두 축으로 나눈 판단**(DEC-2). 코드 파일을 통째로 스캔하지 않고
   상수를 import해 검사한다 — 스캔하면 주석까지 걸려 **정정문 자체를 막는다**.
   또 `workflow/`를 글로브로 넣지 않고 `review-persona.md` 하나만 넣는다(REQ 티켓 문서 보호).
   이 경계가 충분한지, 빠진 배포 표면이 있는지.

3. **D29를 WARN으로 둔 것**(DEC-5). FAIL이면 업그레이드 즉시 기설치 소비자의 커밋이
   서술 문제로 막힌다. 반대로 WARN이면 무시될 수 있다 — 이 절충이 맞는지.

4. **폐기 목록을 shipped 모듈로 옮기는 것**(DEC-4). 테스트에만 있으면 소비자 진단이 볼 수 없고,
   두 벌이면 한쪽만 갱신될 때 진단이 조용히 거짓이 된다. 배포 페이로드 증가는 문자열 ~1KB.

5. **phase 2분할이 독립적인가**(DEC-6). Phase 1만 반영해도 거짓이 사라지는지,
   Phase 2가 Phase 1 없이는 성립하지 않는지.

6. `runChecks` 순수성 유지 — 파일 읽기는 `main()`이 하고 결과만 주입한다는 계약이
   D19·D20·D21 선례와 같은 형태인지.
