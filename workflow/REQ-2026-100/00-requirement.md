# REQ-2026-100 요구사항

## 배경 — 사용자 제기

> "우리 도구를 다른 프로젝트에 적용하고 나면, 매 변경건마다 스위트 테스트니 CI 테스트를 수행하느라
> 수십분에서 많게는 1시간 이상도 걸린다."

원인을 실측했다. 결론부터: **CommitGate가 테스트를 강제하지 않는다.** 느린 것은 관행이고,
그 관행의 씨앗을 도구가 소비자에게 심고 있다.

## 실측 1 — 도구는 테스트를 강제하지 않는다

| 확인 | 결과 |
|---|---|
| `req:doctor`·`req:commit`이 테스트를 실행하는가 | **아니오** — 해당 코드 0줄 |
| `req.config.json` 스키마에 테스트 설정이 있는가 | **없음**(`granularityGate`·`stopGate`뿐) |
| `commitgate init`이 소비자에게 CI를 심는가 | **아니오** |

## 실측 2 — 문서가 거짓을 말하고 있다

[docs/development.md:10](../../docs/development.md)(및 `.en.md`):

> `npm test`는 **전체 스위트**를 돌리고, **게이트 판정도 이것을 봅니다**(변경분만 돌리는 방식은
> 쓰지 않습니다 — 영향 분석이 놓친 회귀를 통과시킵니다).

- **"게이트 판정도 이것을 봅니다"는 사실이 아니다.** 게이트(`req:doctor`·`req:commit`)는 테스트
  결과를 입력으로 받지 않는다. REQ-2026-073이 정리한 것과 **같은 결함 class**(문서가 도구가 하지
  않는 일을 보장).
- 반면 **괄호 안의 거부 근거는 옳다** — 아래 실측 3이 그것을 뒷받침한다. 이 REQ는 그 판단을
  뒤집지 않는다.

## 실측 3 — `vitest --changed`는 이 저장소에서 무용하다

```
npx vitest run --changed HEAD~1
→ Test Files 50 passed (50)     ← 전부 선택
→ 513초                          ← 전체 실행(295초)보다 느림
```

두 원인:
1. **루트 파일 하나가 전 그래프를 무효화한다.** 그때 diff에 `package.json`·`package-lock.json`이
   있었다. 릴리스·의존성 추가마다 재현된다.
2. **모듈 그래프가 넓다**: `review-codex.ts`←17파일 · `req-commit.ts`←8 · `req-doctor.ts`←7 · `req-next.ts`←7.

→ 자동 영향 분석에 게이트를 맡길 수 없다. 기존 문서의 거부 근거가 실측으로 확인됐다.

## 실측 4 — 비용은 테스트 개수가 아니라 프로세스 스폰이다

| 구분 | 파일 | 테스트 | 시간 | 테스트당 |
|---|---|---|---|---|
| 순수(메모리 내) | 18 (36%) | 524 (21%) | **6.1초 (2%)** | 0.84ms |
| 스폰(실 git·실 CLI) | 32 (64%) | 1930 (79%) | ~289초 (98%) | ~150ms |

**테스트당 180배.** 파일 64%가 시간 98%를 쓴다.

## 실측 5 — 범위 한정은 15배, 그러나 대체재는 아니다

REQ-2026-099의 실제 변경(`req-doctor.ts`) → 역의존 7파일 428 tests **20초** vs 전체 295초.

이번 세션 4개 REQ 범위에서는 놓친 것이 없었다(REQ-096에서 깨진 5건이 전부 직접 의존 파일에 있었다).
**그러나 이것은 표본 4건의 관찰이지 보장이 아니다** — 실측 3이 보여주듯 영향 분석은 이 저장소에서
신뢰할 수 없다.

## 관행의 출처

1. [scripts/req/req-new.ts:286](../../scripts/req/req-new.ts)이 **모든 소비자의 `02-plan.md`**에
   `Exit: eslint0·typecheck0 · 단위 그린 · Codex phase 리뷰 승인`을 심는다. 에이전트가 자기 계획서를
   읽고 **매 phase** 실행한다. "단위 그린"이 모호해 "전체 스위트"로 부풀기 쉽다.
2. `AGENTS.template.md` §1 Test-First — 테스트 **작성** 요구지 전량 **실행** 요구가 아닌데,
   실행 시점에 대한 지침이 **아예 없다**.
3. 실제로 이 저장소에서 그렇게 부풀었다 — 2026-08-01 세션에서 REQ 4건에 전체 스위트를 **5회**
   돌렸다(1475초). 도구 요구가 아니라 판단이었다.

## 요구사항

- **R1** — 전체 스위트는 **권위로 유지**한다. 범위 한정 실행이 그것을 대체한다고 말하지 않는다
  (실측 3의 근거는 유효하다).
- **R2** — 전량 검증의 **시점**을 옮긴다: 매 phase → **되돌리기 어려운 지점(통합) 직전**.
  근거는 CommitGate 자신의 구조다 — phase 커밋은 feature 브랜치라 되돌리기 싸고, main 통합은 비싸다.
- **R3** — 범위 한정은 **빠른 피드백 장치**로만 규정한다. 무엇을 보장하지 않는지 함께 적는다.
- **R4** — `docs/development.md`(한/영)의 **거짓 문장**("게이트 판정도 이것을 봅니다")을 정정한다.
- **R5** — 스캐폴드와 에이전트 계약이 R2·R3를 **명시적으로** 말한다. 모호한 "단위 그린"으로 두지 않는다.
- **R6** — 회귀 가드: 정정된 거짓 문장이 문서로 되돌아오지 못하게 한다(REQ-2026-073 선례).

## 범위 밖

- **런타임 동작 변경 없음.** 게이트는 지금도 앞으로도 테스트를 실행하지 않는다. 이 REQ는 그것을
  바꾸지 않는다(테스트 실행을 게이트에 넣으면 fail-closed 계약이 소비자 테스트 품질에 의존하게 된다).
- **`tsx` 기동 제거**(스폰 비용의 94%)는 구조적 개선이지만 **미검증 가설**이다 — 별도 REQ에서
  실측 후 판단한다.
- 소비자 CI 설정은 소비자 것이다. 이 REQ는 `commitgate init`이 CI를 심지 않는 현재 방침을 유지한다.
