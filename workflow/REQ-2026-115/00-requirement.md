# REQ-2026-115 요구사항

D15 정당성 서술 정정 + 관측 로그 오라클 강화

## 무엇을 / 왜

두 건의 작은 정정이다. 둘 다 **선행 REQ의 리뷰·조사에서 나온 것**이고, 각각 독립적이다.

### (1) D15가 자기 정당성을 과소평가하고 있다

D15는 온디스크 응답이 `NEEDS_FIX`인데 `findings`가 비었거나 `next_action`이 공백이면 FAIL한다.
그 코드 주석이 이렇게 적혀 있다:

> `// D15: … (스키마/validateVerdict와 중복이라도 명시 점검).`

**"중복"이 아니다.** 조사 결과:

| 방어선 | `NEEDS_FIX` + 빈 `findings`를 막는가 | 언제 |
|---|---|---|
| JSON Schema(`machine.schema.json`) | ❌ `findings`에 `minItems` 없음 · `next_action`에 `minLength` 없음 | — |
| `validateVerdict`(`review-codex.ts:572~578`) | ✅ | **리뷰 시점** |
| doctor의 `validateResponseStructure` | ❌ **스키마** 검증이라 위 한계를 그대로 물려받음 | 커밋 직전 |
| **D15** | ✅ | **커밋 직전** |

즉 `codex-response.json`이 리뷰 이후 손상되거나 손으로 편집되면 **D15만 잡는다.**
주석은 이 검사를 "있어도 그만"처럼 읽히게 만들고, 그러면 다음 사람이 정리 대상으로 오해한다.

### (2) 관측 로그 테스트가 exit **코드**를 대조하지 않는다

REQ-2026-111의 AC-3("로그 쓰기가 실패해도 출력과 exit 동작이 동일하다")은
`process.exit`의 **호출 여부**만 비교하고 **인자(종료 코드)** 는 보지 않는다.
같은 REQ의 phase 리뷰가 지적한 사항이다.

현재 구현은 기존 exit 호출을 건드리지 않으므로 계약을 만족하지만, 오라클이 그 사실을 고정하지
못한다 — 누군가 `process.exit(1)`을 `process.exit(2)`로 바꿔도 테스트가 통과한다.

## 제약

1. **동작을 바꾸지 않는다.** (1)은 주석, (2)는 테스트다.
2. D15의 판정 로직·메시지·level을 건드리지 않는다.
3. 🔴 정정문에 폐기 문구를 축자 인용하지 않는다(`docs/**`·배포 표면은 가드 대상).

## 완료 기준

| # | 기준 | 검증 |
|---|---|---|
| AC-1 | D15 주석이 **스키마가 이 경우를 막지 않는다**는 사실과 **커밋 직전 유일 방어**라는 점을 적는다 | 문구 확인 |
| AC-2 | 그 주장이 실제로 참임을 **테스트가 고정**한다 — 스키마는 통과하지만 D15는 FAIL하는 응답. **위반을 분리한 두 입력**으로 각 하위 판정을 따로 건다 | 순수 테스트 + 변이 검사 |
| AC-3 | 관측 로그 테스트가 exit 코드의 **동일성과 계약값(`1`)** 을 모두 단언한다 | 변이 검사 |

> 🔴 **AC-2·AC-3의 형태는 설계 리뷰 r01이 고쳐 준 것이다.** 원안은
> (a) 두 위반을 **한 입력에 겹쳐** 두어 한쪽 판정을 제거해도 다른 쪽 때문에 FAIL이 유지됐고,
> (b) exit 코드의 **동일성만** 보아 공통 값을 바꾸면 양쪽이 함께 바뀌어 통과했다.
> 둘 다 "변이 검사를 선언했는데 실제로는 안 잡히는" 형태였다.

## 비목표

- D15 제거·완화 — 조사 결론은 **유지**다.
- 스키마에 `minItems`/`minLength` 추가 — 스키마 변경은 소비자 `sync`가 필요하고,
  이미 두 겹(`validateVerdict`·D15)이 막고 있다. 별건으로도 근거가 약하다.
- 선행 REQ의 **완결된 설계 문서 수정** — 이 저장소 관례상 정오표로만 다룬다(아래 참조).
