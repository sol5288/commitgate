# REQ-2026-176 요구사항

## 무엇

`collectDeepInput`(심층 검증의 입력 수집)의 blob 읽기를
**경로 요청(`<ref>:<path>`) → OID 요청**으로 바꾼다. 읽는 **양은 한 바이트도 바뀌지 않는다** —
`git cat-file --batch` 에 무엇을 써 넣느냐만 바뀐다.

## 왜

REQ-2026-169 가 `req:new` 에서 고친 것과 **같은 원인이 다른 자리에** 남아 있다.
`git cat-file --batch` 는 `<ref>:<path>` 를 받으면 요청마다 트리를 다시 훑고,
OID 를 받으면 objectDB 를 곧바로 친다.

### 실측 (이 저장소, 2026-08-23 · 티켓 166개 · 요청 332경로)

| 요청 방식 | 웜 캐시 | 앞선 콜드 측정 |
|---|---|---|
| `HEAD:<path>` | **581ms** | 5,539ms |
| OID | **88ms** | 310ms |
| 배수 | **6.6배** | 17.9배 |

🔴 **과장하지 않는다.** 절대 절감은 웜 캐시에서 **약 493ms**다.
`npx commitgate verify-range` 전체가 2.6초이므로 그중 **약 19%**다.
콜드 캐시(=CI·오랜만의 첫 호출)에서는 5.2초가 사라진다.

### 이 비용이 지불되는 자리

`verify-range` · `report` · `integrate`(3곳) · `req:delegate` preflight · trunk-advance 인가.
즉 **모든 통합 경로**가 매번 낸다.

### 🔴 왜 지금 고치는가 — 티켓 수에 **선형**이다

읽는 경로 수 = 저장소의 **누적 티켓 수 × 2**(manifest + state)다. 범위 크기와 무관하다.
지금 166티켓에서 493ms이면 500티켓에서는 약 1.5초다.
사용자가 보고한 문제("REQ 가 쌓일수록 계속 느려진다")와 **같은 성격**이며,
이식된 소비자 저장소가 앞으로 겪게 될 마찰이다.

## 🔴 비목표 — 읽는 양을 줄이는 것

"범위 안 티켓의 매니페스트만 읽자"는 **하지 않는다.**
심층 검증은 *"범위 안 커밋을 승인한 행이 어느 매니페스트에 있는가"* 를 찾는 것이고,
그 행이 **어느 티켓 매니페스트에 있는지 미리 알 수 없다**(delivery 묶음이면 다른 티켓에 있다).
좁히면 승인 행을 놓쳐 정상 커밋이 `unattested` 로 떨어진다 — 게이트가 정상 흐름을 죽인다.

→ 이 REQ 는 **같은 데이터를 더 싸게 가져올 뿐**이다. 판정에 쓰이는 입력은 동일하다.

## 완료 기준

1. `collectDeepInput` 이 blob 을 **OID 로** 요청한다(계수 오라클로 고정).
2. 🔴 **추가 git 프로세스가 없다** — 기존 `ls-tree -r --name-only` 를 `ls-tree -r` 로 바꿔
   같은 호출에서 OID 를 함께 받는다.
3. 🔴 **판정이 바이트 동일**하다 — 실 저장소에서 경로 요청 결과와 OID 요청 결과가 같음을 증명한다.
4. 🔴 **배선이 끊길 수 없다** — 새 포트는 **필수 인자**로 둬서 7개 호출부 전부에서 tsc 가 멈춘다.
   (이번 작업에서만 배선 끊김이 다섯 번 났다. 선택 인자는 람다가 조용히 떨어뜨린다.)
