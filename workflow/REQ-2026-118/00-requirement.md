# REQ-2026-118 요구사항

델타 이탈을 리뷰어 재량에서 결정적 조건으로 — full_review_reason 기록

## 배경 (무엇이 문제인가)

델타 설계 리뷰의 이탈 경로(`full_review_requested`)는 **리뷰어 재량**에만 맡겨져 있고, 그 재량은
실측상 한 번도 행사되지 않았다 — 소비자 3곳 누적 0건(과거 0/241 + 신규 관측 필드 도입 후에도
0/1,647행, 2026-08-09 재검증). 같은 기간 설계 재개는 32.6%였다. 설계가 그렇게 자주 다시 열리는데
"이 변경은 델타로 볼 범위를 벗어났다"는 선언이 0이라는 것은, 그 판단을 확률적 신호에 맡겨 둔
구조 자체가 휴면의 원인일 가능성이 높다는 뜻이다(저장소의 기존 교훈: 신호만 있고 발화 조건이
기계화되지 않으면 죽은 기능).

## 요구

- **R1 · 결정적 자동 full 전환** — 다음 조건 중 하나면 델타 모드를 쓰지 않고 **전체 설계 리뷰**로
  전환한다(리뷰어 판단 불요·기계 판정):
  - `all-docs-changed`: baseline 대비 **모든** 설계 문서가 변경됨(델타의 토큰 절감·범위 축소 이득이
    없고, 전면 개정은 전체 맥락 리뷰가 안전).
  - `phase-structure-changed`: 02-plan의 **phase id 집합**이 baseline과 다름(phase 구조 변경은
    승인된 계약의 골격 변경 — 델타 태그로 부분 심사하기에 부적합).
- **R2 · 사유의 구조화 기록** — full 모드로 도는 모든 설계 리뷰에 대해 `full_review_reason`을
  리뷰 호출 로그(`.review-calls.jsonl`)에 선택 키로 기록한다:
  `no-baseline`(첫 리뷰·baseline 부재) · `invalid-baseline`(baseline 손상) ·
  `all-docs-changed` · `phase-structure-changed`. 기존 행(키 부재)은 유효.
- **R3 · 하위호환** — `full_review_requested` 필드·리뷰어 escalation 경로·응답 스키마는
  **변경하지 않는다**(읽기 유지). 이 REQ는 결정적 조건을 앞단에 추가할 뿐, 재량 경로를 제거하지
  않는다(제거 여부는 데이터가 쌓인 뒤 별도 결정).
- **R4 · 표면 노출** — 자동 전환이 일어나면 그 사유를 리뷰 실행 출력에 한 줄로 표시한다
  (사용자가 "왜 이번엔 델타가 아니지"를 물을 필요가 없게).

## 제약

- 승인·차단 판정 로직(`classifyReview`·`validateVerdict`)·응답 스키마·persona 파일 무변경.
- 자동 전환은 **더 넓은 리뷰**로만 움직인다(델타→full). full→델타 방향의 자동 축소는 없다.
- 조건 판정에 필요한 입력은 전부 로컬(git blob·index)이고 네트워크·추가 유료 호출이 없다.
- "중요 인터페이스·스키마 변경" 축은 이번 범위에서 **의도적으로 제외**한다 — 소비자 저장소마다
  무엇이 인터페이스인지 보편·결정적으로 판정할 신호가 없다(경로 패턴은 설정 종속 — 별도 REQ에서
  위험 승격 축과 함께 다룬다).

## 완료 기준

1. baseline 대비 전 문서 변경 → 프롬프트가 full 모드(델타 태그·본문 생략 없음)로 조립되고
   로그에 `full_review_reason: "all-docs-changed"`가 남는다.
2. 02-plan의 phase id 집합 변경(추가·삭제·개명) → full 모드 + `phase-structure-changed`.
3. 일부 문서만 변경 + phase 집합 동일 → 기존 델타 모드 그대로(회귀 없음), reason 키 없음.
4. baseline 부재(첫 리뷰) → 기존 full 모드 그대로 + `no-baseline` 기록.
5. 기존 로그 행(키 부재)은 계속 파싱·유효하다.
6. 자동 전환 시 실행 출력에 사유 한 줄이 나온다.
7. `full_review_requested` 응답 처리(승인 시 baseline 초기화 등)는 무변경으로 그대로 동작한다.
