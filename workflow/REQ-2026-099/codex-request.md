# REQ-2026-099 리뷰 요청 — phase-1-dcheck-table-alignment

## 배경

REQ-2026-097 설계 r02와 REQ-2026-098 phase r01이 각각 비차단 관찰로 문서 불일치를 지적했다.
실측해보니 지적된 것보다 컸다: `07-…md` §3이 "D-체크 정본"이라 선언한 표에 **D20~D27 8행이 통째로
없었고**, "구현된 검사는 13개뿐이다"라는 완결 주장이 거짓이었다(실제 21개). 같은 목록을 복제한
곳이 3군데 더 있었고(`00`·`05`·`12`) 전부 D19에서 멈춰 있었다.

누락된 8건은 전부 WARN 전용이라 **차단 동작이 오기되지는 않았다**(전수 확인). 문제는 존재하는
진단 8건을 문서로 알 수 없다는 것과 완결 주장이 거짓이라는 것이다.

설계는 **r03에서 승인**됐다. r01·r02 P1은 둘 다 DEC-3(재발 가드)에 대한 것이었고 둘 다 옳았다 —
아래 "설계 반려가 남긴 것"에 요약한다.

## 설계 반려가 남긴 것 (r01·r02 P1)

권위를 **관찰**에서 구하려던 두 시도가 각각 반려됐다:

- **r01**: 소스 정규식 → `const id = 'D28'`을 못 뽑는다.
- **r02**: 런타임 변형 합집합 → **비리터럴 id + 그 변형에서 발화하지 않는 조건**이 겹치면 못 본다.

결론은 관찰을 그만두고 **선언된 권위 + 타입 강제**다. 타입 검사는 코드 경로가 아니라 코드 자체를
보므로 표기·발화 조건과 무관하게 등록부 등재를 강제한다.

## 리뷰 포인트

1. **§3에 추가한 8행의 내용이 정확한가.** 각 행의 "FAIL 조건" 칸에 `(WARN 상한, FAIL 아님) 없음`
   표기를 쓰고 실제 WARN 조건을 서술했다. 코드와 대조해 틀린 서술이 있는지 봐달라 —
   **가드는 id 집합만 검사하고 내용은 검사하지 않으므로** 여기가 사람 리뷰가 필요한 지점이다.

2. **DEC-2의 축소가 과했는가.** `00`·`05`·`12`에서 목록을 지우고 §3 참조로 바꿨다. r03 관찰이
   "`12-traceability-matrix.md` 독자가 적용 범위를 이해할 수 있는지 구현 phase에서 확인하라"고
   했다 — 현재 문구(`D-체크 전수(… 예약 결번) — 목록은 07 §3 정본, id 권위는 D_CHECK_IDS`)가
   추적표 독자에게 충분한가.

3. **DEC-3c(죽은 항목 탐지)의 변형 목록.** 4가지 변형으로 21개가 전부 발화한다. 이 목록은 손으로
   유지되며, 낡으면 실패한다(조용한 통과 아님). 유지 비용 대비 가치가 있는가 —
   DEC-3a가 이미 누락을 닫았으므로 이건 보조다.

4. **오라클 자기검증이 충분한가.** `docIds().size > 10`·`D_CHECK_IDS.length > 10`으로 "정규식이
   아무것도 못 뽑았는데 빈 집합끼리 같아서 통과"를 막았다. 다른 자기기만 경로가 있는가.

5. **`Check.id` 좁힘의 파급.** 놓친 소비 경로가 있는가 — 특히 `Check`를 직렬화하거나 외부로
   노출하는 곳.

6. **범위.** D-체크 **동작**은 하나도 바꾸지 않았다. 표를 채우면서 "이 검사는 사실 FAIL이어야
   하지 않나" 같은 논의가 생길 수 있는데 별도 REQ 사안으로 뒀다 — 맞는가.
