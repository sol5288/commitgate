# REQ-2026-099 요구사항

## 배경 — 리뷰가 두 번 지목한 문서 불일치

REQ-2026-097 설계 r02와 REQ-2026-098 phase r01이 각각 비차단 관찰로 같은 종류의 문제를 지적했다:
**문서가 실제 구현보다 뒤처져 있다.**

## 실측 — D-체크 정본 목록이 8건 누락됐다

구현된 D-체크(`req-doctor.ts`의 `id: 'Dnn'` 전수):

```
D2 D3 D5 D6 D9 D10 D11 D13 D15 D16 D17 D18 D19 D20 D21 D22 D23 D24 D25 D26 D27   → 21개
```

문서가 주장하는 것:

| 위치 | 주장 | 실제 |
|---|---|---|
| [07-…md:46](../../docs/ssot-design/07-business-rules-and-state-machines.md) | "구현된 검사는 아래 표의 **13개**(`D2`…`D15`~`D19`)뿐이다" | 21개 |
| [07-…md](../../docs/ssot-design/07-business-rules-and-state-machines.md) §3 표 | D2~D19 행만 존재 | **D20~D27 8행 누락** |
| [00-document-control.md:39](../../docs/ssot-design/00-document-control.md) | 용어표의 D-체크 목록이 D19까지 | 〃 |
| [05-user-flows-and-ui-spec.md:75](../../docs/ssot-design/05-user-flows-and-ui-spec.md) | "D-체크 목록: …D19" | 〃 |
| [12-traceability-matrix.md:21](../../docs/ssot-design/12-traceability-matrix.md) | "D2~D19" | 〃 |

`07-…md` §3은 **D-체크의 정본**이라고 스스로 선언한 표다. 그 표에 없는 검사가 8건 있다.

### 완화 요인(정직하게)

누락된 8건은 **전부 WARN 전용**이다(`level: 'FAIL'`이 하나도 없음 — 전수 확인). 따라서 문서가
**차단 동작을 오기한 것은 아니다.** 사용자가 "왜 막혔는지"를 문서에서 못 찾는 상황은 생기지 않았다.
그러나 존재하는 진단 8건을 문서로 알 수 없고, "13개뿐이다"라는 **명시적 완결 주장**이 거짓이다.

## 두 번째 건 — REQ-2026-098 설계 문서의 테스트 위치 표기

REQ-2026-098 설계는 DEC-5 배선 테스트를 `req-review-codex.test.ts`에 둔다고 적었으나, 구현은
기존 하네스를 재사용해 `review-lifecycle-wiring.test.ts`에 뒀다(phase 리뷰 요청서에 사전 공개,
리뷰어가 "판단은 타당하나 문서와 불일치"로 관찰).

**이 REQ는 REQ-098의 승인된 설계 문서를 고쳐 쓰지 않는다**(아래 요구사항 R4).

## 요구사항

- **R1** — `07-…md` §3의 D-체크 표가 **구현된 검사 전부**를 담는다. "13개뿐이다"라는 완결 주장을
  실제와 맞춘다.
- **R2** — D-체크 목록을 반복하는 나머지 3곳(`00`·`05`·`12`)도 함께 맞춘다. 한 곳만 고치면
  같은 불일치가 남는다.
- **R3** — **재발 방지 가드**를 넣는다. 다음에 D-체크가 추가될 때 문서가 조용히 뒤처지면 안 된다.
- **R4** — 완결된 REQ(098)의 승인된 설계 문서는 **소급 수정하지 않는다.** 승인 시점의 기록이
  감사 대상이다. 정정은 이 REQ의 문서에 **정오표**로 남긴다.

## 범위 밖

- D-체크의 **동작**은 하나도 바꾸지 않는다. 문서와 테스트만 바꾼다.
- 문서-코드 일반 일치 판정기는 만들지 않는다. REQ-2026-044가 "문서 정적 스캐너"를 설계했다가
  오라클을 명세하지 못해 설계 리뷰 5라운드 미수렴으로 폐기했고, 그 결론(DEC-7: 존재 검증만)을 따른다.
