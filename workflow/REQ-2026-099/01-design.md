# REQ-2026-099 설계

> 정본 결정은 SSOT(해당 DEC). 본 문서는 그 결정을 현재 코드/구조에 어떻게 반영할지 기록.

## 현재 상태(변경 대상)

`07-…md` §3이 D-체크의 정본 표라고 선언하지만 D2~D19 행만 있고 D20~D27 8행이 없다.
같은 목록을 반복하는 곳이 3군데 더 있고(`00`·`05`·`12`) 전부 D19에서 멈춰 있다.

누락된 8건과 실제 성격(구현 전수 확인):

|---|---|---|---|

**8건 모두 `level: 'FAIL'`을 내지 않는다**(전수 확인). 표가 뒤처진 동안에도 차단 동작은 오기되지
않았다 — 다만 진단의 존재 자체를 문서로 알 수 없었고 "13개뿐이다"라는 완결 주장이 거짓이었다.

왜 뒤처졌는가: 표는 REQ-2026-014(D19 신설) 시점에 고정됐고, 이후 8개 REQ가 각자 검사를 추가하면서
**아무도 이 표로 돌아오지 않았다.** 사람의 성실성에 기대는 구조라 반복된다 — 그래서 R3(가드)이 있다.

## 핵심 설계 결정

### DEC-1 — `07-…md` §3 표를 구현 전수로 채운다

D20~D27 8행을 추가하고, 각 행의 "FAIL 조건" 칸에는 **FAIL을 내지 않는다는 사실**을 적는다
(D18·D19가 이미 쓰는 `(WARN 전용/상한, FAIL 아님)` 표기를 그대로 따른다 — 새 표기를 만들지 않는다).

§3 서두의 완결 주장을 고친다: "13개뿐이다" → 실제 개수와 목록. **결번 문장(`D1`/`D4`/`D4a`/`D7`/
`D7b`/`D8`/`D12`/`D14`는 예약)은 유지**한다 — 여전히 참이고, 번호 재사용 금지는 살아 있는 규칙이다.

### DEC-2 — 반복 목록 3곳을 같은 커밋에서 맞춘다

`00-document-control.md`(용어표)·`05-user-flows-and-ui-spec.md`(화면 D)·`12-traceability-matrix.md`
(추적표). 한 곳만 고치면 남은 곳이 다음 사람에게 "정본"으로 읽힌다.

🔴 세 곳은 **목록을 다시 나열하지 않고** §3을 가리키는 방향으로 줄인다. 같은 목록이 4곳에 복제돼
있는 것이 애초 원인이다 — 복제를 줄이면 다음 드리프트의 표면이 줄어든다. 다만 `07` §3 자체는
정본이므로 전수를 유지한다.

### DEC-3 — 재발 방지 가드: **런타임 동작이 권위, 소스 텍스트는 규약 강제용**

`tests/unit/docs-stale-claims.test.ts`에 추가한다(문서 진실성 가드가 이미 사는 곳).

🔴 **두 번 반려됐고 두 지적 모두 옳았다. 여기 기록해 둔다 — 이 문제의 난점이 그 자리에 있다.**

- **r01 P1**: 초안은 소스를 정규식으로 파싱해 구현 집합을 얻었다. `const id = 'D28'`처럼 쓰면
  정규식이 못 뽑아 구현·문서가 둘 다 옛 21개로 같아져 통과한다.
- **r02 P1**: 권위를 런타임(`runChecks` 변형 합집합)으로 옮겼더니, **비리터럴 id + 그 변형들에서
  발화하지 않는 조건**이 겹치면 세 집합 어디에도 D28이 없어 여전히 통과한다.

공통 원인은 하나다 — **권위를 "관찰"에서 구했다.** 텍스트 관찰(정규식)도 동작 관찰(변형 실행)도
관찰되지 않은 것을 놓친다. 그래서 관찰을 그만두고 **선언된 권위**를 만든다.

#### DEC-3a — 권위 등록부를 만들고 **타입으로 강제**한다

```ts
/** D-체크 id 전수. 🔴 이것이 권위다 — 여기 없는 id는 타입이 거부한다. */
export const D_CHECK_IDS = ['D2', 'D3', 'D5', … , 'D27'] as const
export type CheckId = (typeof D_CHECK_IDS)[number]
export interface Check { id: CheckId; level: Level; msg: string }   // 기존: id: string
```

이것이 r02 P1의 조합 케이스를 닫는 지점이다. **타입 검사는 코드 경로가 아니라 코드 자체를 본다** —
발화 조건과 무관하고 표기와도 무관하다:

- `c.push({ id: 'D28', … })` → `'D28'`이 `CheckId`에 없어 **tsc 실패**.
- `const id = 'D28'; c.push({ id, … })` → 리터럴 타입 `'D28'`로 추론되어 **tsc 실패**.
- `let id: string = …; c.push({ id, … })` → `string`은 `CheckId`에 대입 불가라 **tsc 실패**.

즉 **등록부에 넣지 않고는 검사를 추가할 수 없다.** 관찰의 사각지대가 사라진다.

실측 전제(현재 HEAD): `Check` 생성 지점 65곳이 전부 `id:` 형태이고, `Check.id`의 외부 소비자는
`tests/unit/req-doctor.test.ts`의 문자열 비교 3곳뿐이다(union↔string 비교는 유효). 좁혀도 깨지지 않는다.

#### DEC-3b — 등록부 ↔ 문서 대조(테스트)

`D_CHECK_IDS`(권위) == `07-…md` §3 표의 `| **Dnn** |` 행 집합. 등록부에 넣었지만 문서에 안 적으면 실패.
유령 행(제거된 검사가 문서에 남음)도 같은 단언이 잡는다.

#### DEC-3c — 등록부의 죽은 항목(부가)

`runChecks`를 입력 변형들로 돌린 `runtime` 합집합 == `D_CHECK_IDS`. 등록부에만 있고 아무 데서도
발화하지 않는 항목을 드러낸다. 🔴 이것은 **보조**다 — DEC-3a가 이미 누락을 닫았으므로, 여기서
변형이 낡으면 결과는 **실패**(조용한 통과 아님)이고 변형을 늘리도록 강제된다.

**연쇄가 각 고리마다 fail-closed다**: 타입(강제) → 등록부(권위) → 문서(대조).

**실측(현재 HEAD)**: 런타임 4변형=21 · 소스 리터럴=21 · 문서 표=13, 차집합이 정확히 `D20~D27`.
이번 phase에서 문서를 채우면 세 축이 일치한다.

- 🔴 **여전히 문서-코드 일반 일치 판정기가 아니다.** 오라클은 "id 집합이 같은가" 하나뿐이고,
  행의 **내용**(검사 이름·FAIL 조건 서술)이 정확한지는 주장하지 않는다 — 사람 리뷰의 몫이다.
  REQ-2026-044가 "문서 정적 스캐너"를 설계했다가 오라클을 명세하지 못해 5라운드 미수렴으로 폐기한
  전례를 반복하지 않는다(그 REQ의 DEC-7: 존재 검증만).
- 실패 메시지는 **어느 id가 어느 쪽에만 있는지**를 말한다. "불일치"만 알리면 고치는 사람이 다시 센다.

### DEC-4 — REQ-098 설계 문서는 고치지 않고 **정오표**로 남긴다

완결된 티켓의 승인된 설계 문서를 소급 수정하면 승인 시점의 감사 기록이 사라진다. `req:commit`이
승인 tree를 해시로 묶는 이유와 같은 취지다. 정정은 이 REQ의 `00-requirement.md`에 사실로 적고,
CHANGELOG에서 언급하지 않는다(사용자에게 영향이 없는 내부 문서 표기 문제다).

## 하위호환·안전

- **런타임 동작 변경 0.** `D_CHECK_IDS`는 새 상수이고 `Check.id` 좁힘은 **타입 수준**이다 —
  방출되는 값·순서·문구가 하나도 바뀌지 않는다.
- **좁힘의 영향 범위(실측)**: `Check` 생성 65곳이 전부 `id: 'Dnn'` 리터럴이고, `Check.id`의 외부
  소비자는 테스트의 문자열 비교 3곳뿐이다(union↔string 비교는 유효). tsc로 확인한다.
- **가드가 보장하지 않는 것**(정직하게): 표 행의 *내용*이 맞는지는 판정하지 않는다.
  DEC-3c의 변형 목록이 낡으면 결과는 **실패**이지 조용한 통과가 아니다.
- 문서 링크는 `npm run docs:lint`(remark-validate-links)가 검증한다.
